# AGENTS.md

The one file of agent instructions in this repository. Every coding agent reads
it under this name, so there is no second copy of it and no symlink standing in
for one.

## Workflow

- After a significant amount of work, commit the changes. If several changes were applied, commit them in such a way each commit represents a feature or unit of work.
- Write unit tests for anything that can have unit tests. Run tests before committing.
- Run `go install` alongside the commit at the end of every unit of work, so the binary on this machine stays current after every change.
- Update this document every time the source code changes, in the same commit as the change, so the two never drift apart. Adding, removing, or repurposing a package, changing the command tree, adding or renaming an environment variable, or changing a convention below all require an edit here.
- `nutshell-spec.md` is a short, human-friendly summary of how a run behaves, written for the user rather than for an agent. It is generated from `nutshell-spec-template.md`, which is the user's own file and is never to be modified: it holds the questions worth answering, and the answers are filled in around them. Regenerating it is not part of every change — it is done when a change alters one of the things the template asks about, and the template is the list of those things rather than anything written here, since the user adds questions to it. When that happens, read the template again and rewrite the document from the current source, in the same commit as the change. A question whose subject was removed keeps its place and is answered as deprecated, which the template says itself: a reader who remembers a feature is owed the news that it is gone. A change that touches nothing the template asks about leaves the document alone; the full account of every convention is this file, and a summary that tried to keep up with all of it would be a second copy of it.
- **`docs/` holds one long document per feature, and none of them is read by default.** They go far deeper than this file does — the whole of a feature's behavior, the alternatives that were rejected and why, and what is known to be imperfect about it — which is exactly what makes reading them all a bad way to start. A document is opened when working on the feature it is about, or when this file points at it, and not otherwise: an agent that reads `docs/` end to end has spent its context on five features to change one. This file stays the map. It says what every convention is, in a paragraph each; a document in `docs/` says why one of them is that way, at length. When the two disagree this file is wrong and is fixed, since a convention nobody can find in the map is a convention nobody will follow.
- A feature with a document in `docs/` keeps it current the way this file is kept current: in the same commit as the change, never afterwards. A document that describes a feature the code no longer has is worse than no document, because it is read as though it were true. The exception is a document that was always a working paper — a plan for work not yet done — which is deleted when the work lands rather than rewritten into a description of it.

## Conventions

- The module path is `github.com/ChrisVilches/agi`. Use the `github.com/ChrisVilches` namespace for any repository URL or module path in this project.
- The CLI is built on [urfave/cli](https://github.com/urfave/cli) v3, where the root command *is* the application. Command wiring lives in `cli/`.
- **There are no subcommands.** Running agi is running the agent on a prompt, and everything that varies a run is a flag on it. A subcommand is added when there is something for it to do, never as a placeholder: a command that parses and then reports it has nothing to do yet is a promise the build does not keep, and it has to be described in `--help` and in the README as though it did. Compacting the context is the one that is wanted, and it is a TODO beside the command tree in `cli.NewApp` until it is specified.
- **Configuration comes from environment variables only. Never use dotfiles.** No `.env`, no `.agirc`, no config file discovery, and no library that reads one. Every setting is an environment variable documented in the table below.
- Tools come in three categories, and they differ in how much the model is told about them. **Native tools** (`tools/native`) are part of the agent itself — subagents, ending the run, loading a skill, and later rewinding and checkpoints — and must be explained in the system prompt, nearly always by implementing `tools.SystemPrompter`. **Workspace tools** (`tools/workspace`) do ordinary work, can be switched off, and must never appear in the system prompt. **User-defined tools** are described the same way workspace tools are. A tool that may not be registered must not be described in the system prompt, so no workspace or user-defined tool implements `SystemPrompter`.
- The rule that matters is the conditionality and not the interface: **an explanation must reach the model only when the tool it is about is registered.** `SystemPrompter` is how a tool that can explain itself does that. `loadskill` cannot, because half of what the model needs is the list of skills this run was given, which is not the tool's to write; its explanation and that list are assembled together in `cli.skillsSection`, from the same list `defaultRegistry` builds the tool from, so a run has both or neither. A second tool wanting the same treatment is a reason to look again at whether the registry should carry it; one exception is a case, two would be a pattern with no home.
- **The category is named for what those tools are and not for what some of them do.** `subagents` and `terminate` really are control flow — one branches the run, the other aborts it — but `loadskill` only puts a document into the conversation, and a category called control flow would have to be read as meaning something other than it means everywhere else in programming. What the three share is that they act on the run rather than on the machine, and mean nothing outside one: they are the agent's own tools, which is what *native* says. A term with a settled meaning outside this repository is never widened to fit a new member; the new thing gets a home of its own, or the category gets an honest name.
- A workspace or user-defined tool's `Description` is the only thing the model learns about it, so the usage rules belong there rather than in the system prompt.
- A system prompt is assembled from a **base**, whatever the registered tools explain, and the skills the run was given, in that order. The base is the swappable half — `prompt.Base()` for an ordinary run, `prompt.Subagent()` for a spawned one — and it must describe nothing agi does, so that replacing it breaks nothing. The native tools' guidance is appended to whichever base is in use, because a model that has not been told what those primitives are for will never reach for them. The skills come last because they are a catalogue rather than an instruction, and a run given none adds nothing.
- **Where a flag's rule is checked is decided by how much of the flag it is about.** A rule small enough to be one comparison about one flag — a number below a floor, a path that is nothing but space — is a `Validator` in `cli.rootFlags`, beside the usage line it belongs to, which is where somebody looking for what a flag accepts is already looking. It buys a message as well: urfave names the flag and quotes what it was given, so the `Validator` supplies only the part the library cannot know, and nothing downstream ever sees a value that failed one. Every path flag shares its rule, so the rule is written once as `cli.namesPath` and `cli.namesPaths` rather than once per flag, and `cli.trimmedPaths` is what reads a repeatable one afterwards.
- **Everything that is not one rule about one flag keeps a function of its own.** Two flags contradicting each other is one: `--rm` and `--session` are refused together in `sessionFlags.open`, because a `Validator` is shown its own flag and nothing else. So is anything where the checking and the work are the same act — reading the files `--sys` names, reading the folders `--resources` names, parsing `--schema`. A `Validator` for one of those would do the work twice, once to find out whether it can be done and once for the value the run uses; a `Validator` doing less than the work would be worse still, letting through what the real read goes on to refuse, in a message the user was told the flag had already accepted. Either way both kinds are checked in `cli` before a gateway is contacted or a session is created, which is the thing that matters — a mistake in how the run was invoked costs a message rather than a run.
- **`--sys` is the user taking that up**, and it is the only part of the prompt they may replace. It names a file — any file, of any extension, since nothing reads it as Markdown — whose text is used exactly where `prompt.Base()` would have been, and nothing downstream is told which of the two it was handed: a base that had to be recognized would not be the swappable half. It may be given more than once, because an instruction is written in parts that are worth keeping apart, and the files are joined in the order the command line gave them, separated by a blank line so each arrives as its own paragraph. Nothing is inserted between them — no heading, no delimiter — because this is one document the user wrote in parts rather than several documents agi is joining; `=== name ===` is for the tools' guidance, which really are separate explanations. The order is never rearranged, since prose read in a different order than it was written says something else.
- **The flag is spelled for the user and not for this repository.** It is `--sys`, short because it is typed often, and everything the user reads about it — `--help`, and the refusals when a file cannot be read — says *system prompt*, which is what the thing is called everywhere outside agi. "Base" is this repository's word for the half of it that can be swapped, and a user typing the flag has no reason to know the prompt has halves at all. The same rule the CLI follows elsewhere: a message is worded for whoever reads it.
- The base is read in `cli` before a gateway is contacted or a session is created, the way an empty prompt and an unparseable schema are refused there, so a wrong path costs a message rather than a run. Every file's text is trimmed, and **a file that is empty, missing, or unreadable fails the run** rather than being skipped: a run has to start from some instruction, and a file that turned out to be empty is far likelier to be the wrong path than a deliberate contribution of nothing. The flag is not an environment variable, for the reason `--schema` is not one: a shell that silently replaced the instruction every run starts from would change every answer agi gave, and the run it changed would look exactly like one it had not.
- **A subagent's base is not swappable.** What `--sys` replaces is the character of the agent the user is talking to; a subagent is not talked to, and its prompt exists to make its reply the kind of thing the `subagents` tool can hand back, so replacing it with a persona would break the one contract a spawned run has.
- Every prompt lives in `prompt/` as its own Markdown file, embedded with `go:embed`. They are kept apart because they change independently, and kept as text because that is what they are. Embedding is not file discovery: nothing is read from disk at run time, and a prompt is not configuration — `--sys` reads a file the user named on the command line, which is an argument to the run and not a file agi went looking for.
- A native tool's guidance reaches the model only alongside the tool it is about — through a registered tool's `SystemPrompt`, or, for `loadskill`, assembled from the same list the tool is built from — and never by unconditional concatenation, and it must describe only the primitives that exist. Guidance for a tool the run was not given is a standing lie to the model, which is the same rule that keeps workspace tools out of the prompt.
- It follows that there is **one guidance file per native tool** — `native-subagents.md`, `native-fork.md`, `native-terminate.md`, and `skills.md` for `loadskill` — and never one document covering several. Each reaches the model only when its own tool is registered, so each has to stand on its own: no shared preamble one of them would be missing, and no file describing a primitive another tool provides. A new native tool brings a file of its own and a `SystemPrompt` returning it.
- `Registry.SystemPrompt` heads each tool's guidance with `=== name ===` before joining them, so a model reading several can tell where one explanation ends and which tool each is about. The delimiter is not a Markdown heading: the guidance is Markdown prose itself, and a heading would dissolve into the text it is supposed to separate.
- Guidance is written short. It says what the tool is, when to reach for it, what conditions a call has to meet, when not to reach for it, and whatever else a model could not work out from the schema — a few paragraphs, each one making its point once. A prompt that argues with itself at length is read less carefully than one that does not, and length is what the tool's own `Description` is for.
- A native tool that needs to run an agent is handed a function that does, rather than reaching for the loop. `cli` wires the registry, so it imports every tool package — `tools/workspace` and `tools/native` alike — and a tool importing `cli` back would be a cycle. `native.Runner` is that function.
- A subagent is an ordinary run: same gateway, same loop, a conversation starting from a prompt. It differs in its base prompt and in what it was given to work with, nothing else. What it may do is settled by which tools are registered for it and never by wording in a prompt — it cannot spawn subagents because no such tool was registered, the same way it cannot use a tool nobody wrote.
- `workspaceRegistry` is the one list of work tools, and both an ordinary run and a subagent build on it, so a tool added there reaches both. Two hand-written lists would make "a subagent gets the same tools minus the native ones" true only by coincidence, and false the next time a tool was added.
- One `subagents` call spawns every task at once and returns the answers in the order the tasks were given, never the order they finished in: the same call must not give the model a different result because of scheduling. A subagent that fails reports it in its own section instead of failing the call, so the answers that did arrive are not thrown away. Their progress is discarded — several at once would interleave into nonsense — so the announced list of titles is the whole of what the user sees while they work, save for the one block `--verbose` prints as each of them starts.
- **A run has three kinds of agent and exactly three levels.** The run itself may fork and may spawn subagents; a fork may spawn subagents; a subagent may do neither. A fork cannot fork, so only one runs at a time and the depth is bounded; a subagent cannot fork, because a copy of a small context somebody else wrote for it is a strange thing to want. Every one of those constraints is enforced by which tools are registered and never by wording in a prompt, which is the rule that already stops a subagent spawning subagents. The shape is asserted whole in one test, because a registration line is one line and nothing fails loudly for deleting it.
- **A fork is a copy of the run, and it exists because the record is append-only.** Every turn but a harness instruction reports `Truncatable() == false`, so an agent cannot do a long piece of exploratory work in its own conversation and then throw the exploration away. `fork` runs a copy of the agent that called it, from the conversation as it stands, on one task, and returns only that copy's final answer as the result of the call; everything else the copy did is discarded. That is what separates it from a subagent, which starts from nothing and has to be briefed. Neither guidance file mentions the other tool, because a run may have either and not the other: each says what its own tool is for, and the model assembles the comparison from whatever it was given. It follows that `prompt/native-subagents.md` may not claim saving context as its purpose, since both tools do that — what tells them apart is the shape of the work, several independent pieces against one that depends on everything said so far.
- **A fork's system prompt is assembled and never copied, and its base is the run's own.** Copying would carry the guidance for `fork` and `terminate` into an agent holding neither, which is the standing lie that keeps workspace tools out of the prompt. The base, though, is the parent's, `--sys` included — and here a fork parts company with a subagent for the reason the subagent rule gives: what `--sys` replaces is the character of the agent the user is talking to, and a fork is that agent, copied. Assembly stays deterministic, as it must for a snapshot to go on storing no prompt at all.
- `forkRegistry` is the one list those two build on: `defaultRegistry` is it plus `fork` and `terminate`, the two tools only the agent the user is talking to may have. A tool added there reaches both, so "a fork gets the run's tools minus two" is true by construction rather than by two hand-written lists staying in step — the argument `workspaceRegistry` makes one level down. A fork also inherits the run's skills whole, the loaded ones included, because a loaded skill's text came across in the conversation and asking for it again would fetch a document already sitting above it.
- **`cli.wiring` is the one value a run's tools are built from** — the output, backend, log, base instruction, backup directory, user tools, skills, turn limit, fan-out limit, terminal cap, the counter that names spawned agents, and the terminals of the agent being built. It passes through everything that builds a registry or starts an agent, so the run, a fork and a subagent cannot be given different things by accident. Four functions each taking the same nine arguments is a claim held together by four argument lists happening to match, and the next value added is the one passed to three of them and forgotten in the fourth. The registry is deliberately not in it: a runner is handed the one its agent's verbose listing compares against, and which that is differs by caller.
- **A fork rewires its own copy of it before it builds anything, and the order is load-bearing.** Everything below a fork is built from whatever wiring it is handed, so the log has to be `Log.Fork`'s handle, the output `output.nested`'s and the terminals a fresh set of the fork's own *before* `forkRegistry` is called. Given the run's, a fork's subagents record under the run's handle and their lines come out unmarked — and that is the one thing a reader could not work out for themselves, since a fork's subagents are numbered in the run's own sequence. `Log.Agent` carrying the mark across only does any good from a handle that has it.
- **A control-flow sentinel must not escape a nested agent, and `cli.contain` is what stops one.** `converse` decides what a tool's error means by its type, so a `*native.Termination` raised inside a fork or a subagent would travel back up and end the whole run rather than that agent — a run ended by an agent the user never spoke to, giving a reason about a task they did not set. Nothing can raise one today, since `terminate` is registered for neither, but that is a single line standing a long way from the damage, which is the same reason `session.Remove` checks the directory's own name rather than trusting its caller's flag. `contain` must not wrap the sentinel: `errors.As` would still find it one layer down and the guard would read as though it worked while doing nothing. `ErrInterrupted` passes through untouched, because the parent is meant to see that one.
- **A fork is watched on screen where a subagent is silent.** Subagents are dropped because several run at once and their steps would interleave into a page belonging to no agent; only one fork runs at a time and the agent that asked is blocked while it works, so there is nothing to interleave with. Its progress streams through `output.nested`, marked line by line with a marker distinct from `indent`'s, since a fork's own tool output is marked by `indent` before it is marked again on the way out. Its answer is not printed there: that is a tool result, which the agent loop already prints. A `--verbose` run adds one block as the fork starts, from `forkIntro` — never a preview, which would describe an agent the run may never spawn.
- **`eventlog` marks everything recorded inside a fork.** `Log.Fork` sets the flag and `Log.Agent` carries it over, so a subagent a fork spawned is marked without anything having to remember to do it; the field sits beside `Agent` because the two together are the line's identity. `fork.start` and `fork.finish` bracket the work and are kinds of their own rather than a subagent's, since kind is what a reader filters by. The flag is what tells two agents apart that a name cannot, which matters because the numbering is the run's: `native.Counter` is created once per run and shared by every `Subagents` tool in it, the run's own and each fork's. Those names are also filenames — a `patchfile` copy is filed under the agent that made it — and a directory of file copies has no field saying which side of a fork a line was on.
- A conversation is a sequence of typed messages — `UserMessage`, `AssistantMessage`, `ToolResultMessage`, `ToolFailure`, `SubagentResults`, `HarnessInstruction` — not one struct with optional fields. The set is closed by an unexported method on the `Message` interface, so a new kind of turn is added in `model` and nowhere else. Tool requests live inside `AssistantMessage`, because that is how they arrive: one turn may request several tools.
- `model.Conversation` owns the rules about how turns may follow one another, including when a run is finished and which tool requests are outstanding. Logic of that kind belongs there rather than in the agent loop, so the loop only has to do the work in between.
- A turn holds what it means and renders what it sends. `HarnessInstruction` stores the instruction and adds its delimiters in `Render`; `SubagentResults` stores each subagent's answer under its own title and concatenates them in `Render`; `ToolFailure` stores the reason a call could not be made and marks it as an error in `Render`. Text a model reads is assembled at the moment of sending and never stored assembled, so the structure survives into a session snapshot instead of becoming a blob that would have to be parsed back apart.
- The turns that answer a tool request implement `model.ToolAnswer` — an answer, a refusal, a set of subagent answers — and everything that treats them alike, validating that a result answers a request that was made or encoding a turn for a gateway, goes through that interface. Another kind of answer is added by implementing it, not by finding every switch that would otherwise need to learn about it.
- A distinction that outlives the moment is a type, not a flag. A call that could not be made at all is a `ToolFailure` rather than a `ToolResultMessage` with a boolean on it, so a resumed conversation and anything that displays a turn can still tell a refusal from an answer. A tool that ran and reported a problem of its own — a command exiting non-zero — is an ordinary result, because the model reads the output and decides what to do about it.
- A tool with more than a string to report implements `tools.Resulter` and builds its own answering turn; `Registry.Answer` prefers it and wraps every other tool's text in a plain result. `Tool.Call` stays as it is, so a tool has to opt in and the agent loop appends one turn either way.
- A tool that cannot answer from its arguments alone implements `tools.Conversational`, which `Registry.Answer` prefers over both, and is handed a function that **forks** the conversation rather than the conversation itself: such a tool has a reason to branch from the record and none whatever to write into it. The registry relays that function and never holds a conversation. It follows that `Conversation.Fork` does the whole close-out in one method — the call that asked answered, anything asked alongside it answered as a call that was not made, the instruction appended — because all of it is a rule about how turns may follow one another, and three steps that must always happen together in one order are not three steps. The instruction is a `HarnessInstruction` and not a user turn: the model wrote the task and agi is relaying it. `Fork.Call` has to exist because `tools.Tool` is what the registry accepts, cannot work, and refuses saying so; narrowing the interface to delete it would trade a compile-time guarantee covering every tool for one method on one.
- A turn is either record or scaffolding, and the type says which. The rule that matters is about the record: what the user asked and what the model answered are kept exactly as they arrived, never rewritten and never dropped, only appended to. A `HarnessInstruction` is agi speaking to the model in its own voice — it travels under the `user` role because no provider has one for the harness, and `Render` wraps it as `[Instructions] Follow these instructions: …` so the model does not read it as the user interrupting. Being scaffolding, it is the only turn that reports `Truncatable() == true`, which is permission rather than obligation: an instruction may be dropped once it has served its purpose, or may stand for the whole run.
- `Conversation.DropFrom` is how scaffolding comes back out when a caller decides it should. It removes a tail that must begin at a truncatable turn, taking the exchange that answered it along: those turns exist only because of the instruction and mean nothing without it. The check on the first turn is what stops the record being cut. A caller that means to remove an instruction takes a mark with `Len` before appending it and unwinds on every path out, so a conversation resumed later carries no trace of how the run was steered.
- agi reports itself in three ways, and they are separate mechanisms with separate purposes rather than three settings on one. **Terminal output** is for a person watching a run: it exists to be read at a glance, so it is styled, deliberately partial, and discarded when nobody is at a terminal. A **session snapshot** is the conversation as it stood when the run finished, and exists so that the next run can continue it. The **log** is the stream of everything that happened, written to a file for tracing and reproducing a run afterwards. Nothing may be added to one of them on the grounds that it would be useful in another.
- The log is `eventlog/`: one JSON object per line, appended to `log.jsonl` in the session's directory and never to a terminal. A debugging stream on stdout would corrupt whatever is reading the pipe, and on stderr it would bury the diagnostics `--verbose` puts there, so a log goes to a file or nowhere. `--no-log` is nowhere: the log becomes a pass-through that answers every call and writes nothing, which is also what a run with no session directory gets.
- **The log is append-only and is never rewritten.** When a run takes turns back out of the conversation — the scaffolding of a schema phase, say — the removal is itself an event. What the snapshot drops, the log keeps, which is why the log and not the snapshot is what to read when asking what actually happened. It follows that a snapshot must never be made inspectable at the cost of restoring cleanly: that job is already taken.
- **Every harness instruction is recorded as it is appended, in full.** An instruction is agi steering the run in its own voice, so a run steered by words nothing kept is a run that cannot be read back — and the reader worst served is whoever is debugging a fork, since one instruction is the whole of what the copy was told to do and it is a fixed wrapper around a task the log would otherwise hold alone. `cli.instruct` appends and records in one call so that neither can happen without the other, and the one instruction it does not cover is the one `Conversation.Fork` appends itself, recorded beside it into the fork's own log so the line lands under the fork's name. The lines around an instruction keep what is theirs and not its text: `fork.start` carries the task the tool was called with, `schema.rejected` the verdict on an attempt, and `schema.restate` the shape that was asked for — each true whether or not an instruction followed.
- A log is safe to share because a channel carries every event to one writer goroutine, which is the only thing that touches the file. Subagents record alongside the run that spawned them and alongside each other, so this is not incidental. Recording never fails the run either: an event that cannot be written is dropped, and `Close` reports the first write that failed, once.
- Interleaving is a problem for a display and not for a log, since every line says which agent wrote it. So a subagent is silent on screen but records everything an ordinary run records, under a name of its own, and a run that fanned out can still be read back in full.
- A subagent's name is settled before any of them starts, from the order the tasks were given, and the numbering keeps counting across calls so a run that fans out twice does not reuse the first group's names. A name taken from which goroutine started first would be scheduling deciding what a reader sees, which is the rule that already puts the answers in the order they were asked for. `native.Brief` is how the number reaches whatever runs the subagent; `eventlog.Log.Agent` takes the name it is given and invents nothing, because only the caller knows what tells two nested runs apart.
- A log line carries no sequence number. One goroutine writes the file and appends each line as it arrives, so the lines of a run are always in the order they were recorded, and a number saying so would repeat what counting them already tells you — and would lie in the one case where a file really can interleave, two runs sharing a session directory, since each numbers from one.
- **What a line says comes before the bookkeeping for joining lines together.** The keys come out in the order `eventlog.Event` declares its fields, so the struct's field order is the file's format and reordering it is a format change. `kind` leads because it is the field a reader filters and groups by, and every other field on the line only means anything once it is known. `request_id` and `time` trail, because neither says anything to somebody reading one line — one is an opaque identifier and the other a fixed width of digits, and in the middle of a line each is that much further to the part worth reading. Both ends are asserted in a test rather than left to whoever edits the struct next.
- An `eventlog.Event` is one struct for every kind of event, with `kind` saying which fields mean anything — the same bargain `session`'s stored message makes, because a file has no closed set of types to switch on. Add a kind to `eventlog` and record it where the thing happens; never let a caller assemble its own line.
- **A kind names its subject and then what happened to it**, `run.answer` and `model.response` and `tool.call`, because a reader filters and groups by kind and a bare word gives them nothing to group with. The prefix is also what keeps two kinds apart that ordinary English does not: `model.response` is one reply from the model, of which a run has many, and `run.answer` is the prose the agent loop ended on, of which a run has one — as words, *response* and *answer* are synonyms, and which was which could only be looked up rather than read. It is `model.` rather than `gateway.` because a gateway is only one of the things that can be at the other end, and the `openai` backend fronts nothing.
- The system prompt is recorded in the log, which is the other half of not storing it in a snapshot. It is assembled from how agi was invoked, so a snapshot that kept a copy would go stale; a log without one would describe a run nobody could reproduce.
- The prompt has three spellings and one meaning. It is the single positional argument, or, when there is none, everything on standard input up to EOF, or nothing at all — so a here-document, a file, or another program's output can be the question. Whichever it is, the prompt is trimmed, and an empty one is refused in `cli` before a gateway is contacted or a session created. Nothing downstream is told which spelling was used, which is why `--schema` and the session flags need no say in it: they are flags on a run, not on where its prompt came from.
- Standard input is read the same way whoever is on the other end of it: a pipe, a file, or a person who typed `agi`, typed the prompt, and ended it with Ctrl-D. agi prints nothing to announce that it is reading — a line explaining Ctrl-D would be in the way of everyone who already knew, every time, which is the same reason progress output is dropped when nobody is watching.
- **agi waits for a prompt to be typed only when someone is there to type it.** Anything piped or redirected into standard input holds a prompt and is read to EOF, whatever it turns out to contain. A terminal on standard input holds one only when standard output is a terminal too: agi was started with its answer going to the screen, so whoever started it is watching and can type. A terminal on standard input with standard output redirected or piped — `agi > result`, `agi | jq` — is no prompt at all, and is refused as an empty prompt without standard input being touched. Reading it would wait for a Ctrl-D nobody is going to press, and a program that hangs forever is worse than one that says what is missing. Both halves of the rule are in `cli.holdsPrompt`, which takes the two answers as booleans so every branch can be tested without a terminal, the way `cli.route` does for output.
- Stdout is two different channels. At a terminal it is a display for a person, and tool calls, reasons, and the answer all belong there. When it is piped or redirected it is a channel to another program, so it must carry the final answer as plain text and nothing else. The agent loop prints progress through `output.step`, which is discarded when stdout is not a terminal, and the answer through `output.final`, which always reaches stdout.
- **An error is printed on standard error as it is, with nothing in front of it, and every error is printed the same way.** No program-name prefix: whoever ran agi knows what they ran. No per-error formatting either — a message that needs a case of its own in `main` is a message whose wording is wrong. `main` is the only place an error is printed, and the only thing it varies is the exit status. **That includes an error a flag made**, which is what `cli.usageError` is for: urfave/cli otherwise answers a bad flag by writing `Incorrect Usage`, the message, and the whole help text to standard error, and then returning the same error for `main` to print a second time. The hook hands the error back unchanged, and the help is no loss — a user who mistyped one flag is told which flag and what was wrong with it, and a screen of every flag agi has is what buries the one sentence that matters.
- `--verbose` while piping is a request for diagnostics, so the progress stream goes to stderr rather than stdout, leaving the data channel clean.
- **A run says where it is being kept twice, at both ends, and says it as the flag that names it.** `cli.sessionLine` is the whole of it: `--session /tmp/agi-1b2` and nothing else, dimmed like the rest of the progress stream. It is written as the flag rather than as a sentence about the directory because the line is there to be pasted — a conversation is continued by giving agi the same directory again, so what is on the screen is the whole of the next command but the prompt, and the user types their next question after it. It is said at the top for somebody who wants to look inside the directory while the run is going, and again at the bottom because by then whatever the run printed has pushed the first line off the screen, and the moment the directory is worth having is the moment after the answer has been read. **A `--rm` run says it once, at the top**: its directory is removed by the deferred call that runs as `runPrompt` returns, so a closing line would name a path that was gone by the time it was read, where during the run it is there like any other.
- A verbose run opens by saying what it is about to do the work with, and `cli.preamble` is the whole of it: the model and the address it is reached at, the shape the answer must take, the system prompt in full, and every registered tool's name and `Description`. What those have in common is that they decide how the run goes, the user did not supply them, and they are assembled from how agi was invoked rather than stored anywhere — so a run watched without them can only be guessed at. The tools' **parameters are deliberately left out**: a JSON Schema object is several times the length of the prose beside it and answers only what shape a call takes, which the log already records for every call actually made. It is printed from `runSession` rather than beside the run's other opening lines because the system prompt does not exist until it is assembled there. This is not the terminal borrowing the log's job: the log is read afterwards and in full, while this is written to be read as the run happens and is discarded when nobody is watching.
- **A tool is explained once and then only named.** A subagent's tools are mostly the run's own, so a second full listing would bury the one thing that list is for — which tools the agent has — under paragraphs the user read a moment ago and has to compare against the first listing to discover say the same thing. A repeat is named and marked `explained above` instead. What counts as already explained is the `Description` and not the name, because a tool may one day be described differently to two agents when what it can do for each differs, and pointing the user upward at a description this agent does not read would be worse than saying nothing. It is checked rather than assumed: `cli.toolList` compares the text.
- **The preamble says nothing about subagents, and each subagent says it about itself as it starts.** What a run could say in advance is what *some* subagent would get, and there is no such agent: which skills one is given is decided task by task, when the model writes the brief. A run used to describe a fabricated agent built for the purpose, under a name no subagent has, and what that agent got was the tools and the prompt of a subagent with no skills — so a run whose real subagents all read a skill showed the user a prompt none of them read, and showed it as though it were the answer. The preview and the fake name went with it; nothing in agi builds an agent it will not run.
- `cli.subagentIntro` is what replaced it, printed from `subagentRunner` once per subagent, out of the same `agentSetup` the preamble uses because there is nothing different to say about a spawned agent. It carries the name the run records under, the task's title, the system prompt in full — which is where the skills are, since the prompt lists them, so there is nothing separate to print for them — and the tools. **A block is assembled in full and written in one piece**, because subagents start at the same moment and two blocks several screens long would otherwise interleave into a page belonging to neither; a mutex in `subagentRunner` lets one through at a time. Which block comes first is whichever agent got going first, so every block names its own agent and stands alone: nothing a reader needs may depend on the order they arrive in.
- Naming a tool rather than explaining it again works across those blocks the same way it worked inside the preamble, and it is the reason `subagentRunner` is handed the run's own registry. It asks `cli.explainedBy` what the run's listing said, and that is a fresh map per subagent: they run at once, and one shared map would be several goroutines writing into one. Asking the registry rather than assuming the descriptions match is what keeps the rule below honest — a tool described differently to a subagent is explained again.
- Whether stdout is a terminal is a separate question from whether color is enabled: `NO_COLOR` at a terminal means plain progress output, not no progress output. Detection lives in `cli.isTerminal`, and routing in `cli.route`, which is kept separate so every branch can be tested without a terminal.
- Terminal styling goes through the helpers in `tools` (`tools.Name`, `tools.Detail`) rather than raw escape codes, so a tool decides which part of its output is a command or a detail, and the styling stays consistent. Color disables itself when output is not a terminal and when `NO_COLOR` is set.
- **Only the sixteen named colors are used, and never a hex or 256-color value.** What agi looks like is then decided by the palette of the terminal it is running in, which is where the user has already chosen it, rather than by a number written into the source that fights whatever theme they picked. **Subordinate text is a second voice rather than a faded one**, and `tools.Detail` is blue, which two earlier attempts argue for. It was bright black, the color a great many themes draw almost on top of their background, so the lines it marks — the `--session` line at both ends of a run, a command under its reason, every line of tool output — were there to be read and could not be. It was then white, which is the terminal's default foreground, so those lines looked like ordinary text and were marked as nothing at all. A different color sorts them from the text around them at a glance and no theme hides it. Green was never a candidate, since it means success everywhere else. **`tools.Name` is the opposite of that and is bold yellow**: the `[tool]` label is the one word on the screen that says a call is happening at all, so it is the thing to be drawn to, where everything under it is there to be found once you have been. It was cyan, a neighbor away from the detail lines' blue, and a label beside its own detail in a neighboring color is a block of one wash rather than a heading and what it heads — which is the test any future pair of colors here has to pass.
- **`tools.Detail` styles a line at a time, and text handed to it may be several.** A single span opened on one line and closed on another asks the terminal to carry the attribute across the line break, and a great many do not: a multi-line `bash` command came out colored on its first line and plain on every line after it. So each line opens and closes its own, and a blank line is left alone, since there is nothing there to color. It belongs in the helper rather than in the one caller that showed it, because three of them can be handed more than one line — a command's announcement, a user-defined tool's, and any error whose message wraps.
- A tool says two things to the person watching, and they are different things. `tools.Announcer` describes a call before it happens — what it is for, and the command or the text it is about. `tools.Reporter` describes what came back, for the one or two tools whose result is worth a line: `mktemp` reports the directory it made, because the path is the only thing about a scratch directory nothing else records, `patchfile` reports where it put the copy of the file it changed, because that is the way back from a change that turns out to be wrong, `loadskill` reports the directory the skill came out of, because what reaches the model is the skill's own text and nothing in it says which folder on the machine that was, and `terminal_open` reports the number it handed out, because every later terminal call is shown by that number and nothing else on the screen would have named it, with how many terminals are open beside it, and `terminal_close` reports how many are left for the same reason read backwards — closing is the only moment the number goes down, and neither the announcement, which names the terminal that was asked for, nor the result, which is one sentence about its program, says that one of them really went. **That count is in the result and not only in the line under it**, because a report is skipped under `--verbose`, so a count that lived only there would be missing from exactly the runs that show the most; the line is then cut back out of the result, the way `loadskill`'s directory is, so the user is shown the number the model was told rather than a second count taken a moment later. **It is worded `2 terminals now open`, and says the count alone.** `2 of 8 open` was tried and read as naming terminal 2 among eight that were open, since a count and a terminal's own number are the same kind of word and `of` between two numbers is how an item in a list is named everywhere else. The cap is what put a second number there, and the cap is not what the line is for: nothing says the cap to the model until it reaches it, and a user watching a run wants to know how many terminals are open rather than how many more are allowed. So the number is said with the thing it counts and with when it is true, which leaves nothing for it to be mistaken for. A report is a line or two and is skipped under `--verbose`, which already prints the whole result; anything longer is not a report but the result itself, and has a place already.
- **How much of an argument an announcement shows depends on what the argument is, and there are two answers.** `tools.SingleLine` is for an argument whose point is what it names rather than what it says — the path `writefile` is writing to, the text `patchfile` is replacing — where a full listing would push the next call off the screen and the first line is enough to recognize the call by. It lives in `tools` rather than beside one tool, because a workspace tool and a native one both announce a call this way and the question they answer is the same — the argument that put `Truncate` there. `block` stays in `tools/workspace/display.go`, since only workspace tools use it. `block` is for an argument the user has to read in full to know what is about to happen, which is the command `bash` runs and the keys `terminal_send` types: it is the thing happening to their machine, and the line that matters is as often the last as the first — the redirection at the end, the second command after the first. A command is therefore never abbreviated, however many lines it runs to. `block` leads the first line with `$` and pads the rest to where that line's text starts, so the call reads as one block in the shape a terminal transcript has rather than as several calls; a blank line inside it stays blank rather than becoming padding nobody can see, and the command's own indentation is left exactly as it was, since it was written to be read the way the shell reads it.
- agi targets only the **intersection** of what mainstream LLM providers support: a conversation of `system`, `user`, and `assistant` messages, and tool calling. That intersection is the whole feature surface, and it is a deliberate ceiling rather than a stage on the way to something richer.
- The reason is that a gateway fronts many providers, and anything outside that core is supported unevenly, behaves differently, or is rejected outright depending on what sits behind the gateway. Building on it would mean either a feature that silently degrades for some providers, or per-provider branching that the `transport.Client` interface exists to avoid.
- In particular, do not add support for **prefix completion** — prefilling the assistant's next turn to steer raw inference — or for **structured output**, meaning schema-constrained or JSON-mode responses. Several current models reject assistant prefill with an error, and structured-output support varies in both syntax and semantics. Where output shape matters, ask for it in the prompt and validate what comes back; where steering matters, use the system prompt or a tool.
- **A model's own reasoning is not read.** A thinking model returns the deliberation behind its reply in a `reasoning_content` field; `transport/openai` declares no such field, so it is discarded where the reply is decoded, and nothing is ever sent back in one. What reading it would add is something to watch, and what it would cost is a thing agi holds and can do nothing with: no mainstream provider accepts it as input, so it can never inform a later turn, and it would have to be kept out of a snapshot by a rule rather than by not existing. The thinking that does survive a turn is the prose a model writes alongside its tool calls, which is what `prompt/base.md` asks for.
- **The default model is chosen to suit the default base prompt, because that is the pair almost every run uses.** `prompt.Base()` tells the agent to think on the page, and warns that reasoning it skips is reasoning it does not get to use. A model with nowhere else to think obeys that literally: its deliberation lands in the reply, stays in the conversation, and is re-read on every turn after. A thinking model has somewhere else to put it, and what goes there is discarded when the turn ends, so the same instruction buys less. `deepseek-chat` is therefore the default and `deepseek-reasoner` is not, though the two reach the same model and the thinking one answers a one-shot question better. Neither half is fixed — `--sys` replaces the prompt and an environment variable names the model — so this is a default that suits a default, not a claim about which model is better. Changing one is a reason to reconsider the other.
- **A provider that requires reasoning handed back is out of scope, and it is a wall rather than a bug.** Some do: Anthropic rejects an assistant turn whose signed thinking blocks are missing when extended thinking and tool use are both on, and Moonshot's Kimi thinking models require `reasoning_content` preserved on every historical assistant message. Through a gateway these arrive under names of their own — LiteLLM renames Anthropic's to `thinking_blocks` — so supporting any of them means the shared client reading a field, keeping it on the assistant turn, and echoing it, which puts it in the snapshot and makes `transport.Client` provider-aware. That is the ceiling two rules above, so the requirement is deferred rather than the ceiling weakened. Nothing is reachable today: it needs a model of that kind named in `LITELLM_MODEL` *and* tools in the run. A TODO, not a plan.
- The shape of an answer is therefore asked for and checked locally, never requested from the provider. `model.Schema` is that check: a flat set of named scalar fields (`string`, `bool`, `int`, `decimal` — nothing optional, and no field holding a list or an object), parsed from the `--schema` spelling `id:int:"User ID", name:str:"Full name"`, with `ValidateJSON` reporting every way a document fails to match it in a single error so one correction can fix all of them.
- **A schema asks for one object or a list of them, and that is the only nesting the DSL has.** Brackets around the whole spec — `[id:int, name:str]` — set `Schema.List`, and the answer is then a JSON array of objects with those fields, the empty array included: a run that found nothing to list has still answered. The brackets go around the whole spec and nowhere else, so a list inside a list and a field holding one (`names:str[]`) are both refused by `unwrapList` while parsing, before a gateway is contacted. The restriction is the point rather than an unfinished corner: a flat shape is the most a model can be relied on to produce from a prompt alone, and one list of flat objects is what the answers that are not a single set of facts actually look like. `Schema.Describe` renders the fields the same way either way, because they are the same fields; that they arrive as an array is `cli.schemaInstruction`'s business, and it spells the two shapes out separately rather than describing an object and adding a line about wrapping it. Problems inside a list name the item they were found in (`item 2: missing field "rate"`), and once `maxBadItems` items have gone wrong the rest are counted rather than described, so a long bad answer cannot turn the correction into an instruction longer than the answer.
- A `--schema` run is the ordinary run plus a second phase, never a different run. The agent loop ends the way it always does, on a prose answer, and only then is the model asked to restate that answer as JSON, up to `maxSchemaAttempts` times, each rejection handed back as a harness instruction saying what was wrong. The reasoning is asked for in prose rather than read off the model's hidden reasoning, which only some providers expose. Attempts that run out fail the run: a wrongly shaped document is worse than none for whatever is reading the pipe. The whole phase is dropped from the conversation before returning — instruction, attempts, and the accepted JSON alike — leaving the prose answer as the last word.
- The prose answer is the deliverable without a schema and the reasoning with one, so with a schema it goes to `output.step` and the JSON to `output.final`. A piped schema run carries the document alone.
- **A run is bounded by a number of turns, and the bound is a stop rather than a budget.** One turn is one exchange with the model, and a run that reaches the cap gives up with no answer at all, which is the worst thing a run can do; the turns a long run spends before it answers are work the user asked for. So `defaultMaxTurns` is 200 rather than a tight number, and a cap low enough to cut an honest run short would trade every answer of that kind for the minutes a runaway loop costs.
- **`--max-turns` is the user changing it**, and it is a flag rather than an environment variable for the reason `--schema` and `--sys` are: a shell that quietly lowered the cap would make runs give up that would otherwise have answered, and the run it changed would look exactly like one it had not. It is checked by the flag's own `Validator`, before a gateway is contacted or a session is created, because a cap too small to answer in is a run that was never going to answer, and finding it now costs a message rather than the turns it was allowed. The whole of the rule is one comparison against a constant, which is what puts it on the flag rather than in a function of its own.
- `minMaxTurns` is 5 and is a floor rather than a suggestion. The first turn is rarely the answer — an agent calls a tool, reads what came back, and often corrects a call that went wrong — so a handful of turns is the least a run that touches a tool at all can finish in, and anything smaller could only end in giving up. The refusal names the smallest cap, since a user who asked for one turn wants the number and not an argument.
- **One cap is given to every agent of a run, the subagents included.** A spawned run is an ordinary run, and a user who raised the cap because the work is long did not mean it for only some of the agents doing that work. The number reaches `converse` as an argument rather than being read there, because how long a run may go on is settled by the command line and the loop is the last place that would know it.
- **How wide one `subagents` call may fan out is the run's to decide too, and `--max-subagents` is where it is decided.** `defaultMaxSubagents` is 8, and the flag is a flag rather than an environment variable for the reason `--max-turns` is: a shell that quietly narrowed every fan-out would change how the work got done and say nothing about it. It reaches the tool through `wiring`, so the run and each fork are held to the same number — a fork spawns subagents, and one built from a wiring of its own would otherwise be free to spawn a different number than the agent that copied it.
- **The cap has a floor and no ceiling.** The floor is `native.MinTasks`, checked by the flag's own `Validator` before a gateway is contacted, because a cap below the fewest tasks a call may carry is a tool no call could ever be made to. The constant is exported for that check and is not respelled in `cli`, since two spellings of one number are two floors the first time either is changed. There is no ceiling and no overflow check: what a wide fan-out costs is conversations open at the gateway at once, which is the user's money and the user's judgement, and a number agi invented would be a guess standing in the way of somebody who meant what they typed.
- **`native.MinTasks` is 2 and is not something a run may change.** One subagent is never worth the round trip — the parent waits on an agent that knows less about the problem than it does, for work it could have finished in the time it took to write the brief — and that is true of every job, however long. The maximum is about the work and belongs to the run; the minimum is about the tool and belongs to the tool. `NewSubagents` raises a cap below the floor back to it rather than advertising a width it would refuse every call at, which is what a caller with no opinion — a test, the throwaway registry that collects the reserved names — gets.
- Every run is kept unless the user says otherwise. `session/` stores one in a directory — holding the snapshot and, unless `--no-log` says otherwise, the log — a fresh one under `TMPDIR` by default, and the one `--session` names if it is given. The two flags contradict each other and are refused together. **Every session has a directory**, and there is no second kind with nowhere to write: `New`, `Open`, and `Ephemeral` all produce one, nothing outside the package can build a `Session` without it, and so no caller anywhere asks whether there is somewhere to store things. There used to be a `Discarded` session that stored nothing, and it was removed because nothing in agi ever made one — only tests did, and what it bought them was a branch in `LogPath`, `BackupDir`, `Lock`, `Load`, `Save`, and `patchfile`'s own description, each guarding a case the program could not reach. A state only a test can produce is a state the code should not carry.
- **`--rm` removes a session rather than never making one.** The run gets a directory of its own and uses it like any other run — it writes a snapshot, records a log, and its tools keep whatever they keep — and `session.Remove` deletes the directory when the run ends, however it ends: an answer, a failure, the user stopping it, the model ending it. The alternative, a run with nowhere to write, would have to be taught to every mechanism that writes anything, and would take away from `--rm` the one thing a run needs a directory for while it is still running. A run killed outright — a second Ctrl-C, or a signal agi does not handle — leaves the directory behind under `TMPDIR`, which is the one gap and is not worth closing by handing the shutdown something that can itself be interrupted. `--rm` does mean the conversation touches the disk before it is deleted, where a run with nowhere to write never would.
- Removal is deferred before the log is opened, because deferred calls run in reverse and the log has to be closed first: closing it is what waits for the writer goroutine to be done with the file, and a directory removed before that is a goroutine writing into nothing. The two lines are load-bearing in that order.
- **The rule that keeps a user's conversation safe lives next to the line that would delete it.** `Remove` deletes nothing unless the session marked itself ephemeral, which only `session.Ephemeral` does, and unless the directory's own name carries the `agi-` prefix — so a session the user named can never be deleted, and neither can one wrongly marked. Both checks are in `session`, not in the caller: `--rm` and `--session` being refused together is a rule in `cli`, one flag away from a deletion two packages down, and a guarantee that far from the damage stops holding the first time somebody adds a caller. The check is on the prefix rather than on `/tmp`, because where sessions are made follows `TMPDIR` and a fixed path would fail every legitimate removal on a machine that points it elsewhere.
- `--session` names a directory that must already exist, and a name matching nothing is an error rather than a new session. Naming a session is asking for one conversation in particular, so a name that finds nothing is a mistake — a typo, a path from another machine, a value the shell mangled — and starting an empty session under it would answer the user's question as though the ones before it had never been asked. A run that names no session still gets a directory of its own, so this takes nothing away. The value is trimmed first, because it arrived as a shell argument and space around a path is never part of the path: left alone, a leading space turns an absolute path into a relative one, and `"   /tmp/chat"` is a directory called `"   "` in the working directory with `tmp/chat` inside it.
- Passing the same `--session` directory again is the entire chat mechanism. `Session.Resume` loads the stored conversation and appends the new prompt as the next user turn, so running agi twice is a two-turn conversation and nothing in the agent loop needs to know which it is.
- **A session belongs to one run at a time, and the lock that says so is the operating system's.** `Session.Lock` takes it when a run starts and `Lock.Release` gives it back however the run ends; a second agi process that names the same session is refused with `session.ErrLocked` before anything is written. Both files in the directory assume one writer and neither says so: two runs finishing at once leave whichever snapshot was written last and the other run's turns are gone, and the log, being appended to rather than replaced, keeps both runs' lines shuffled into one another with each numbering its turns from the beginning. Locking is what makes "a session is a conversation" true rather than merely usual.
- The lock is `flock` on a hidden `.lock` file in the session's directory, rather than a file whose existence is the lock. It is hidden because it is not part of what the session holds: a session directory is a conversation and the record of how it was produced, and this is agi's own bookkeeping, empty and never read. The processes to be kept apart are separate invocations sharing nothing but the filesystem, so a mutex would order only the goroutines inside one of them; and the kernel drops an `flock` when the process holding it dies, however it dies, so a run killed outright leaves no stale lock to be cleaned up or overridden. Nothing removes the lock file, because unlinking it on release is the one way to reintroduce the bug it prevents — a second run can hold the file open at the moment it is unlinked, after which a third creates a fresh file at the same path and locks that instead. The file is empty and stays empty: a pid written into it would be a fourth account of the run, and a stale one, answering worse the question the lock already answers. It is `syscall.Flock`, so it is a unix lock and the package does not compile on Windows — a build failure rather than a lock that silently does nothing, which is the right way round for a mechanism whose job is keeping two processes apart. Windows is a TODO in `session/lock.go` and is not to be answered with a no-op.
- Taking the lock sits between removing the session and opening the log, which is the order the deferred calls give it: the log is closed first, because a log still being written is a run still using the session; the lock is released next; and the directory `--rm` asked for goes last, since there is nothing to release once it is gone.
- **A snapshot stores what was said, and nothing that is assembled from how agi was invoked.** The system prompt is the case in point and is deliberately not stored. Nobody says it: it is built from the base prompt and the tools a run registers, so a session resumed with different tools or a different base is owed the prompt its own arguments describe. Storing a copy would mean keeping data that goes stale the moment an argument changes — and that nothing reads, since `Resume` supplies the prompt either way. The invocation is the source of truth.
- That holds only because assembling a prompt is deterministic: the same arguments and files must always produce the same prompt, and nothing in `systemPromptFor` may depend on the time or the run. Treat it as an invariant, and keep the test that asserts it.
- A snapshot exists to restore a conversation, not to explain one, so nothing is kept in it for the sake of debugging. Questions of that kind are the log's, once there is one: it records every event in order, including what was later truncated, so a run can be reproduced from it in full and what the prompt was at any point simply follows. Nothing has to be stored beside the conversation to make that answerable.
- A snapshot is agi's own account of what was said, not a provider's: a `HarnessInstruction` is stored as a harness instruction, since the user role it travels under is the gateway's business. The file format lives in `session/` and is kept apart from `model` for the same reason the wire format is. It carries no version: agi runs from a fresh install against sessions that install made, so there is no older format to recognize, and a file this build cannot read still fails loudly because an unknown turn kind is refused rather than guessed at. The snapshot is written only when a run finished, so a failed run leaves the session at its last complete exchange.
- **Ctrl-C ends a run rather than killing it.** The signal cancels the context every part of the run is waiting on, so the request in flight and the command a tool is running stop where they are, and the run then finishes the way it always does: the conversation is stored, the log is closed, and `run.interrupt` records the turn it stopped at. That is the one departure from the rule above, and it is narrower than it looks — a failed run is one agi cannot vouch for, so storing it would be storing a guess, while an interrupted one is not in doubt and throwing it away would discard work the user watched happen. Signal handling goes back to the operating system as soon as the shutdown starts, so a second Ctrl-C kills agi outright, and an interrupted run exits 130 rather than 1 so a shell can tell it from a failure. The interruption is reported once, as the run's error, which `main` prints on standard error like any other; `abandon` prints nothing itself, since at a terminal the progress stream and standard error are the same screen and the user would read it twice.
- **The model can end a run that cannot be answered**, which is what gives agi the other half of unix process semantics: `terminate` in `tools/native` ends the run where it stands, nothing is written to stdout, and agi exits non-zero — 1, the status any run that produced no answer gets. It is for a request that cannot be understood, needs something the run was not given, or names something that does not exist with no one to ask; it is not for work that was merely hard or only partly successful, since an incomplete answer is worth more than none. The optional `reason` is the whole of what the user gets and reaches them on standard error, printed by `main` rather than through the progress stream a piped run discards.
- A termination is stored like an interruption and for the same reason: everything said was said and nothing about it is in doubt, unlike a failure agi cannot vouch for. The call that ended the run is answered in the conversation with a plain result saying the run ended, and whatever was asked alongside it is abandoned — a provider may refuse a turn that moves on from an outstanding request. That answer is never sent: the run is over, nothing would read the reply, and asking the gateway again would buy a round trip agi throws away. It exists so the snapshot resumes cleanly, and resuming appends the new prompt after it — tools are not re-run on a resume, so the run does not end itself again.
- A run stopped in the middle of a batch of tool calls leaves requests nobody answered, and a conversation stored like that cannot be resumed: a provider is entitled to refuse a turn that moves on while a call it asked for is outstanding. `Conversation.AbandonToolRequests` answers each of them with a `ToolFailure` saying the run was interrupted, which is what a failure is for — a call that could not be made — and the record stays intact because nothing is rewritten or dropped. A tool killed by the same signal is answered the same way rather than reporting an error of its own: `bash` returns the cancellation instead of the exit status a signal leaves behind, since it did not refuse the call and there is no next turn in which to correct anything. Resuming afterwards appends the new prompt after the old one, and two user turns in a row are an ordinary conversation to every model.
- `transport/` owns every exchange with an external backend. Two interfaces come out of it, and the difference between them is the point. `transport.Client` is a conversation in and a reply out, and it is all the agent loop needs, which is why a run can be exercised without a network. `transport.Backend` is a `Client` that has been configured and can say how — which model, and at which address — because a run reports both in its log and under `--verbose`, and the configured backend is the only thing that knows. Each backend gets a subpackage.
- **The model a run is on belongs to its backend, not to a request.** `transport.Request` carries no model name: one backend, one model, named in that backend's own environment variables and read back through `Backend.Model`. A field on the request as well would be a second place for the same answer to live, and the two would disagree the first time something forgot to fill one in.
- The protocol is written out in `transport/openai` and not taken from a vendor SDK. What agi needs from a provider is a list of messages, a list of tool definitions, and one reply — a few hundred lines of JSON structs and a POST. A code-generated SDK would be the largest dependency in the module by a wide margin, and it would put every provider-specific extra one autocomplete away from a project that caps its feature surface on purpose.
- It follows that there is one client and several configurations of it. Every endpoint agi talks to — OpenAI, DeepSeek, a LiteLLM gateway fronting either — speaks the OpenAI chat completions protocol, so `transport/litellm` says where to send a request, under which name, and on which model, and `transport/openai` makes it. Two hand-written clients for one protocol would drift apart the first time either was corrected. A backend that needs a genuinely different protocol is a different client; a backend that needs different variables is a `Config`.
- A configuration says who it is. `openai.Config` carries a `Name` and a `URLVar` that no request uses, so that a failure names the backend the user configured and the variable they have to fix, rather than this package's own. A gateway misconfiguration that sent someone after `OPENAI_URL` would be advice that leads away from the problem.
- Backends are opt-in and never assumed, and so is the choice between them. `AGI_BACKEND` has no default: two backends exist, they read different variables, and picking one silently would make the likelier mistake — configuring one and forgetting to ask for it — report the other one's variable as missing. There is no default address either, so agi contacts nothing until it is told where, and the Go module must not take on a dependency on any gateway.
- Each backend reads its own variables and nothing else's, all of them prefixed with its name: a gateway's address, key and model say nothing about a direct provider's, and the reverse. The one value shared between them is `openai.DefaultModel`, because a default that was written out once per backend would be two defaults the first time one of them was changed. `cli.backends` is the one list of what `AGI_BACKEND` accepts; adding a backend is a line there and a row in the table below, and nothing in the agent loop changes, because the loop only ever sees a `transport.Backend`.
- The tools in `tools/workspace` are peers, and being written in Go buys none of them standing. `bash`, `mktemp`, `patchfile`, and `writefile` are described the same way, through `Definition` alone, and any of them may be absent from a run. It follows that a description may not lean on another tool being registered: it says what its own tool is for and what it is not for, and the model assembles the comparison from whatever it was actually given. A group document explaining when to use which would be read by a run that has only one of them, which is the same standing lie that keeps workspace tools out of the system prompt. **The four terminal tools are the one exception, and only among themselves**: they are one tool split by what a call does, registered together or not at all, so each description names the others by the constants in `tools/workspace/terminal.go` — and none of them mentions `bash`, which a run with terminals may still lack.
- Every tool that hands a program's output back to the model has the same problem with an oversized result and no reason to answer it differently, so cutting one down is `tools.Truncate` and not each tool's own helper. It keeps both ends and says between them how much was dropped, because where a long result was cut has to be visible or the model reads what is left as the whole of it. The limit stays the tool's own, since what counts as too much depends on what the tool produces.
- **A cancelled command takes everything it started with it, and `tools.KillGroupOnCancel` is how.** Killing a process does not kill what that process started: a `bash` command line holding more than one command leaves the shell alive as a parent, so killing the shell would orphan its children rather than end them, and the orphans would go on doing whatever they were doing — a find over the whole disk, a connection to a server that will not answer. Those are the cases Ctrl-C is pressed for, so a Ctrl-C that leaves them running has not done what the person meant by it. Each command is therefore made the leader of a process group of its own and the whole group is killed when the context is done, which reaches every descendant however deep, since a process group is inherited the way a pipe is. Every tool that runs a program has the same problem and no reason to answer it differently, so the helper is in `tools` rather than in each of them — the argument `tools.Truncate` already makes one field over — and `tools/workspace`, `tools/userdefined` and `hooks` all call it.
- **It fires on cancellation, which includes a timeout, and never on a command that finished by itself.** That line is the whole of the feature's restraint: a model that deliberately leaves something running in the background keeps it when the call succeeds and loses it when the run is stopped. Killing the group at the end of every call would take the first away and nothing would say so, which is why there is a test pinning each side. It is SIGKILL rather than a SIGTERM first, because the run is being abandoned and there is nothing for a graceful shutdown to be graceful for; the default it replaces already killed the direct child outright.
- **`cmd.WaitDelay` stays beside it, at two seconds, and both are wanted.** A descendant that put itself in a group of its own — anything that calls `setsid`, which is what a daemon does — escapes the signal and can still hold the output pipe open, and a read waiting for end of file would then be waiting for it rather than for the run. Unbounded, that wait is what Ctrl-C could not get past: the run sat there until the straggler happened to finish, and the second Ctrl-C killed agi outright and lost the snapshot, so the interruption rule below was making a promise it did not keep. The bound is written out in each of the three rather than shared, since each is bounding its own cleanup and has its own reason to change.
- **One consequence of the process group is easy to miss:** a command is no longer in agi's own process group, so a Ctrl-C typed at a terminal no longer reaches it directly and the kill above is the only thing that ends it. That is more deterministic than what it replaces, where a command died of the terminal's signal at a terminal and of nothing at all when agi was piped, but it does mean a command is killed rather than interrupted and one that cleaned up after itself on SIGINT no longer gets to.
- An agent that needs somewhere to put something asks for it: `mktemp` makes an empty directory and returns the path. The harness does not make one in advance, does not name one in the system prompt, and does not pass one in the environment — a directory nobody asked for is a directory the model has to be told about, and telling it means describing in the prompt a thing that workspace tools are not allowed to put there. Asking also settles per-agent and per-run collisions for free, since `os.MkdirTemp` makes the name unique by creating it, and subagents work at the same time.
- **Nothing removes a scratch directory, and nothing is meant to.** Cleanup would mean deciding when an agent has finished with something it was never asked to account for, and guessing wrong destroys the one copy of a file the run was relying on. They are made under `TMPDIR` rather than in the session's directory, so agi's own snapshot and log stay out of reach of a model that goes looking, and so a session stays what it is: a conversation, not a conversation and a pile of files. The names share the `agi-scratch-` prefix, because nothing else records where they are and a listing has to show which directories are agi's. The purpose the model gave is not in the name: it is a phrase written to be read as the call happens, and folding one into a path segment produced names long enough to be worse than no name at all. What each directory was for is in the conversation and in the log.
- `patchfile` changes a file by replacing text that appears in it **exactly once**, and that is its whole safety property rather than a convenience. A match that appears twice means the model has not said which place it meant; a match that appears nowhere means the file is not what the model thinks it is. Both are refused, and they are refused with different wording, because the two mistakes are corrected differently — one by including more of the surrounding text, the other by reading the file again. Matching is over the file's bytes and not its lines, which is what makes a file that ends without a newline patchable at all, and nothing is added or removed at the end of a file on its own. It follows that a successful patch has nothing to count: the result says the one match was replaced and the rest of the file left as it was, rather than reporting a number that could never have been anything but one. The call is announced as two lines, the outgoing text marked `-` and the incoming one `+`: both are arguments, so both are known before anything happens, and a deletion shows the `-` alone because that is what a diff of one looks like.
- `writefile` creates a file that is not there yet, and **only** creates one: a path that already holds anything is refused and left as it was, so no call to it can destroy work. That guarantee comes from opening with `O_EXCL` and not from the check that precedes it — the check exists to say which of the several things that can be wrong actually is, and the flag exists because between looking and writing anything could have happened. The three refusals are worded apart from one another because they are corrected differently: something already at the path means choosing another name, a missing directory means creating it first, and a permission the operating system withheld means not writing there at all. Existence is tested with `Lstat`, so a symbolic link is something at the path whether or not it points anywhere; following one would write through a link nobody asked about, which is the opposite of `patchfile`'s rule for the same reason — changing a linked file is ordinary, creating one behind a link is not. **No directory is ever created**, because making the parents of a path on the model's behalf turns a typo into a tree of empty directories and still does not write the file that was meant; the missing directory is named back instead. Content is written byte for byte with nothing added, an empty content makes an empty file, and a write that fails partway removes what it made, so a failed call leaves the path as it found it.
- A tool that rewrites a file writes it alongside and renames it into place, the way a session snapshot is written, so a run stopped midway cannot leave a half-written file where a whole one used to be — and it carries the original mode across, since `os.CreateTemp` makes a private file and renaming that over a script would take the execute bit off it. A symbolic link is followed rather than refused, and the link itself is left where it is: linked configuration files are ordinary, and a rename over the link would quietly turn it into a regular file.
- **A tool that changes a file the user already had keeps a copy of it first, and that is the tool's business rather than the model's.** `patchfile` does: every call writes the file as it was into the session's `backups/` before touching it. A copy the model has to decide to take is a copy it will sometimes not take, and those are exactly the calls that turn out to have needed one. It follows that the advice to copy something first belongs only in tools that really cannot undo what they do — `bash` deleting or overwriting a file, and `mktemp` as the place to put the copy — and that `mktemp`'s description may not claim that nothing in the run can undo a change, because that stopped being true.
- The copy is taken once the call is certain to go ahead, after every refusal and from the bytes already read, so a patch that matched nothing leaves nothing behind and a file about to be rewritten is not read twice. A copy that cannot be written fails the call: patching anyway would break the one promise the description makes, in the case where it turns out to matter.
- A copy is named `<UTC timestamp>-<agent>-<file's own name>`, and the order of those three is the whole design. The timestamp leads because sorting the directory by name has to be the same as sorting it by age — with nobody at a terminal, that is the only way to find the earliest copy of a file, which is the one that is the original. It is UTC and fixed width for the same reason: local time repeats an hour a year and would sort an evening's copies backwards. The agent follows, because subagents patch at the same time as each other and two copies made in the same instant have to be told apart; it is the name the run records under, so `eventlog.MainAgent` is exported rather than a second spelling of `main` existing. The file's own name is last and is there to be read. The file is created exclusively, since the one case where a name could be taken is two agi processes sharing a session, which nothing yet prevents.
- Two files of the same name in different directories become two copies that nothing in the name distinguishes, and that is deliberate — it is the same trade `mktemp` makes by not folding a purpose into a directory's name. What is not in the name is in the log, which records the call's arguments and its result against one request id, so the file a copy came from and the copy's path are read together. **That is also why no event kind was added for this:** both paths are already recorded, and a line assembled for something the log already holds would be a second account of it.
- **Every run keeps copies, so the promise is unconditional.** `patchfile`'s description always carries the paragraph about the copy, and `Call` always takes one, because every session has a directory and `Session.BackupDir` always names a place inside it — `--rm` included, since an ephemeral session is an ordinary one until the run ends. The description used to leave the paragraph out when there was no backup directory, which was the rule that keeps an unregistered tool out of the system prompt applied to a tool's own description; it went when the case it guarded stopped existing. If a run that keeps no copies is ever wanted again, the paragraph has to come back with it: a promise the run cannot keep is worse than no promise, because it would have the model skip the copy it should have taken itself.
- Nothing prunes the copies, the way nothing removes a scratch directory, and for the same reason: deciding a copy is no longer wanted means deciding that on the user's behalf. They go when the session does, which for `--rm` is at the end of the run.
- The copies live in the session directory but are not a fourth way agi reports itself. They are the user's files, kept; the snapshot, the log, and the terminal remain the three accounts of what happened, and none of them may borrow this one's job either.
- **Restoring a copy is not implemented yet.** The path is in the result the model reads, so a model that wants a file back can read the copy and write it out, and a person can copy it back by hand. What does not exist is anything that does it deterministically, and that is where reverting a patch belongs when it comes.
- **A tool does not have to be written in Go, and one that is not is a tool like any other.** `tools/userdefined` runs an executable the user wrote, in whatever language they wrote it in. It is the third category the `tools` package already names, and it is described to the model the way a workspace tool is — by its `Definition` and nothing else — so it contributes nothing to the system prompt and a run may have been given none of them.
- A folder's tools are declared in a `tools.json` at its root, and that file is the whole of what agi knows about them. It is a JSON array of entries and nothing else: nothing is discovered by looking around the folder, so a script that is not listed is not a tool, and a tool that is listed and missing fails the run rather than quietly disappearing from it. Each entry gives a `name`, a `path`, a `description`, and `parameters`, which are the same four things a Go tool's `Definition` gives.
- **A TODO that can only be done together with others is tagged, so the set can be found at once.** There is none at present — `TODO(--resources)` was the one, and it was paid when the three flags became `--resources`. The convention stands for the next one: an ordinary `TODO:` stays untagged, and a tag is for a debt that is paid in one place or not at all, so that `grep -rn 'TODO(<tag>)'` lists every site of it and nobody is tempted to fix one site alone.
- **One folder holds everything a user brings to a run, and each kind is announced by a name of its own.** `tools.json` declares the tools, `hooks.json` declares the hooks, and the skills are the folders under it that hold a `SKILL.md` — there is no `skills.json`, because a skill is made by writing one and nothing has ever declared one. A folder need not hold all three: a folder with no `tools.json` declares no tools, and that is nothing to report. A folder that holds none of the three is refused, since naming a folder is asking for what is in it, and a folder with nothing in it is the wrong path far more often than it is a deliberate request for nothing.
- **Refuse a mistake; accept a declaration that says none.** A `tools.json` holding `[]` and a `hooks.json` holding `{}` are accepted and bring nothing, which is what an absent file already means. Both were once refused on the grounds that somebody wrote the file and meant something by it, and that was wrong: an empty declaration is not ambiguous, nothing downstream then misbehaves quietly, and emptying a file is how a person switches something off without deleting what they mean to write again — the more so now that one folder carries all three kinds, where refusing the whole run over one empty file throws away the tools and skills beside it. What stays refused is a file that cannot be read as what it claims to be: a name that is not an event, an entry with no program, a script without the executable bit. Those are mistakes. Declaring nothing is a decision, and the two files answer it the same way, because one refusing what the other accepts would be a worse surprise than either rule.
- **A filename that says what the file holds is what keeps the two packages apart.** The tools and the hooks used to share one `manifest.json` under a top-level key each, and the price was that each package declared the *other's* key as a field it read and threw away — both decoders refuse a field they do not know, so a folder holding both halves would otherwise have loaded as neither. Two packages that should know nothing about each other each named the other's word. Neither does now, and neither may again: a new kind of resource gets a file of its own rather than a key in somebody else's. The whole of the hook feature is `docs/hooks-specification.md`, which is read when working on hooks and not otherwise.
- **The name of a tool and the name of the file that runs it are different things**, which is why `tools.json` lists them separately. What a script is called on disk is the user's business and is usually not what the tool should be called when a model reads a list of them, so `fetch-weather-v2.sh` is the `path` and `weather` is the `name`. A name has to be one a provider will accept — letters, digits, underscores, hyphens — and a name that would be rejected in the middle of a run is refused before the run starts.
- The protocol between agi and a script is this, and it is what `tools/userdefined`'s package documentation describes in full. The script is executed directly and never through a shell, so it has to be executable and has to begin with a shebang naming its interpreter; nothing in an argument can be read as a command. It is given exactly one argument, the JSON object of arguments the model produced — named parameters are the reason it is one JSON argument rather than several positional ones, since a script takes what it needs from the object and adding a parameter renumbers nothing. It inherits agi's environment and working directory, which is the whole of how a user-defined tool is configured, and its standard input is empty so that a script reading it finds end of file rather than waiting for input that is never coming.
- **The exit status decides which stream the model reads.** Zero is success and standard output is the result, so a script may log freely to standard error. Anything else is failure, and standard error is the reason, or standard output when standard error is empty. A script should therefore explain itself in words either way — what it did on success, why it could not on failure — because the model reads one stream and nothing else.
- The two outcomes reach the conversation as the two types that already mean them: a `ToolResultMessage` for success, and a `ToolFailure` for a non-zero exit. This is not the exception to `bash` reporting an exit status as an ordinary result; it is the same rule read properly. A command `bash` ran is the model's own composition, and its status is one more thing to read. A user-defined tool's status is the tool itself saying the call did not happen, which is what a `ToolFailure` is for.
- Everything about a folder is checked when the folder is read, before a gateway is contacted or a session is created, the way `--sys` and `--schema` are. A `tools.json` that is not valid JSON, an entry with no description, a `path` that names nothing, a file without the executable bit: each is a mistake in how the run was invoked, and it costs a message at the start rather than a failed call in the middle of a conversation the user is paying for. An unknown field in an entry is refused too, since every one of them is a typo with a silent version — `paths` would be a tool with no script.
- A `path` is relative to the folder and never leaves it: an absolute path or one climbing out with `..` is refused. A folder of tools is a thing that can be moved, copied, and handed to somebody else, and a `tools.json` reaching outside itself would be one that works on the machine it was written on and nowhere else.
- **A user-defined tool's arguments are checked before its script is run**, so a call the tool would have refused never reaches it, and every problem with one call is reported at once so a correction can fix all of them. That is why only part of JSON Schema is accepted in `parameters`: agi will not advertise a constraint it does not enforce. The keywords it checks are `type`, `description`, `properties`, `required`, `items`, `enum` and `additionalProperties`; a `tools.json` using any other is refused when it is read, with the keyword named. `additionalProperties` means what JSON Schema says it means, because the same object is what the provider is shown and the two must not disagree about it.
- **`--resources` is how a folder reaches a run**, and it is one flag over the three kinds rather than one flag each. It is a flag rather than an environment variable for the reason `--sys` is: a shell that silently added tools to every run, or armed a guard on one, would change what the agent can do to the machine, and the run it changed would look exactly like one it had not. It is repeatable, because a folder of resources is a thing kept somewhere and reused, and the alternative is a folder of symbolic links to the folders the user actually meant. The folders are read in `cli`, before a gateway is contacted or a session is created, so a mistake in one costs a message rather than a run, and `cli.resourcesFlag` is where all of it happens — it reads the three kinds, refuses a `--resources` that is not a folder, and refuses one that brought nothing.
- **Naming a folder brings in everything in it, hooks included, and that promise was traded deliberately.** Three flags could say that a folder of tools does not arm the guards in it until the user asks for them separately, and one flag cannot. What replaces it is that the folder is the user's own and they named it; an opt-in per kind would be three flags again under another spelling. This is the one thing the merge could not keep, and it is not to be reintroduced as a fourth flag.
- **The order the folders were given in is kept all the way through, and within a folder each kind keeps the order it was written in.** It decides two things. Hooks run in sequence and one hook's output is the next one's input, so rearranging them would change what a tool is finally called with; and the skills are listed to the model in this order, so two runs naming the same folders must produce the same prompt, which is the invariant that lets a snapshot store no prompt at all. Tools are the exception that proves it: the model is offered them by name whatever order they arrived in, so nothing depends on theirs, and they are still not rearranged because the order is not agi's to decide.
- User-defined tools are registered in `workspaceRegistry` and not beside it, so a subagent gets them for the same reason it gets `bash`: there is one list of work tools, and two hand-written lists would make "a subagent gets the same tools minus the native ones" true only by coincidence. A tool the user brought is a work tool in every way that matters — described by its definition alone, silent in the system prompt, absent from a run that was given none.
- A user-defined tool may not take the name of one agi provides. That is refused in `cli` where the user can act on it, worded for somebody looking at a `tools.json`, and the names are asked of the registry through `providedNames` rather than written out, so a tool added to either list is reserved by that alone. `Registry.Register` refuses it too, later and in this repository's words, which is the backstop rather than the message.
- **Two tools of the same name fail the run, wherever the two came from.** The model addresses a tool by its name and could not tell them apart, so which one wins is not a choice agi may make quietly; the message names both files and says to deduplicate them. The folders themselves are not rearranged or sorted — they are read in the order they were given, and the registry offers tools to the model in name order however they arrived.
- **A skill is a folder holding a `SKILL.md`, and the file is what makes it one.** Nothing declares a skill anywhere, so one is added by writing it and removed by deleting it. `skills/` is the search: it is given folders to look in and descends until it reaches a `SKILL.md`, which it reads, and it goes no further down that path. There may be any number of folders on the way, because a folder holding no `SKILL.md` is only somewhere skills are kept — `go/testing/SKILL.md` is the skill `testing` and not a skill called `go` — and there is nothing below one, because every file and folder under a skill is that skill's own resources.
- **A `SKILL.md` under a skill fails the search rather than being ignored**, since both readings of it are wrong: as a skill it is one whose id would be a folder nobody would look for it in, and as a resource it is a file announcing itself as a skill and then being read as prose. Which the author meant is not agi's to guess, and the fix — move it out, or rename it — is theirs.
- **A skill has an id and a title, and they do different jobs.** The id is the name of the folder the `SKILL.md` is in, and it is the skill's identity: it is what `loadskill` is called with, what a subagent's task names, and what no two skills may share wherever they were found. The title is the `name` the frontmatter gives, it is prose written to be read — `ssh-usage` titled `SSH Usage and Efficient Commands` — and it is held to nothing: two skills may carry the same title, and one that repeats the folder's name costs nothing. The frontmatter's name used to have to match the folder exactly, which made the two one thing and left the title no job to do; what made a matching name worth having was that a skill is referred to by one, and that is the id's work, which cannot drift from where the skill is because it *is* where the skill is. Two skills with one id are refused with both places named, because which one wins is the user's to decide and not agi's to decide quietly.
- A folder is read on its own terms first — every `SKILL.md` under it found and parsed — and only once every folder has been read is the one question that spans them asked, which is whether two skills have the same id. Collisions reported before the folders were known to be sound would be reported against skills that might turn out not to be skills at all. The first thing found wrong ends the search and is the error returned; there is no partial result, since a caller wanting the skills it can get is asking a different question and would have to be told which ones were missing.
- A named folder that is not there fails, the way `--session` does and for the same reason: a name matching nothing is a typo, a path from another machine, or a value the shell mangled, and answering as though the folder had been empty says something else. A folder that really is empty is no error **to this package** — it holds no skills, which is a thing a folder of resources is allowed to be, since it may hold tools or hooks instead. Whether an empty folder is worth naming at all is a question about the flag and is answered there: `cli.refuseEmptyFolders` refuses a folder that brought the run none of the three, so `--resources` on a folder that is empty today fails even though the search over it did not. The two are not in disagreement — one asks what is in the folder and the other asks whether naming it meant anything — but they answer differently, and only the second is what a user sees. The path is trimmed before it is used, since space around a path arrived from a shell and is never part of it. A symbolic link to a folder is not descended into, which keeps the search finite whatever the folder holds and keeps a skill from being brought in from outside the folder the user named.
- The frontmatter is YAML between `---` lines and nothing else, though the library reads TOML and JSON too. A `SKILL.md` is written for whatever reads skills and every one of them writes YAML; two further spellings would be two further ways for a file to be read differently here than it is everywhere else, and `tags`, the one field with a shape of its own, would quietly stop working in both. `name` and `description` are required, `version` and `tags` are not, and `tags` may be written as one string or as a list because both say the same thing to whoever wrote the file. `name` is collapsed onto one line where it is read rather than where it is shown, because a title is a name and a name with a line break in it is not one — a description is prose and may honestly have been written across several lines, so that one is stored as it was written and collapsed by whatever renders it.
- **A frontmatter field agi does not know is left alone**, which is the opposite of what a `tools.json` does with one and is the right way round for both. A `tools.json` is written for agi, so a field agi does not know is a typo. A `SKILL.md` is written for whoever reads skills, so a field agi does not know is a field somebody else reads.
- `skills.Find` is the whole of the package's surface, and it takes a list of folders because reading one is calling it with one. The frontmatter is parsed by `github.com/adrg/frontmatter` rather than by hand: unlike the chat protocol, this is a small settled format with an established parser and no provider-specific corners to keep out, so the argument that keeps an SDK out of `transport/` does not reach it.
- **The skills of a run are the ones kept under the folders `--resources` named**, found the way `skills.Find` finds them and never declared anywhere. There is no `skills.json` beside the other two files, because a skill is made by writing a `SKILL.md` and unmade by deleting it, and a file listing them would be a second answer to which skills a folder has. A folder holding nothing but skills is an ordinary folder to name.
- **The skills are the last part of the system prompt**, after the base and after everything the tools explain. They are the one part that is a catalogue rather than an instruction: by the time the model reads a name, it has been told what to do with it. The section is headed `=== skills ===` for the reason the guidance sections are headed — the prompt is Markdown throughout, and a Markdown heading would dissolve into the prose it separates — and it is one section rather than two because an explanation with no list describes a tool with nothing to call it on, and a list with no explanation is a set of names the model has no reason to think it may ask for. `prompt/skills.md` is the explanation, since it is the same every run; `skills.Describe` renders the list, since it is this run's.
- **A skill is summarized in the prompt and loaded on demand.** The list gives the id in bold, the title in quotation marks after it, one line of description, and the tags where there are any — never the instructions, which are the whole point of loading one and would otherwise be carried by every run whether it needed them or not. **An entry has to make plain which of the two names can be called with**, since a model reading one line has to get it right without looking anything up: the id leads and is the only thing in bold, the title follows in quotation marks, which is how a line of prose says it is naming something rather than saying it, and a title that is only the id over again is left out entirely rather than have the model compare two spellings of one word. `prompt/skills.md` says the same thing in words, and `loadskill`'s one argument is called `id` rather than `name` because the schema is the one place a model reads about a call with no prose around it.
- `loadskill` takes the id and nothing else: where a skill is on disk was settled when the folder was read, and a model that could name a path could name any path. **What comes back says where the skill is**, in a line above the document and outside the tag that wraps it, because a skill mentions the files beside it by a path relative to its own folder and nothing else in the conversation says what those paths are relative to. The line is agi speaking rather than the skill's author, which is why it is outside; it comes first so the model has read it before it reaches the first such path; and the same line is what the tool's `Report` cuts a directory back out of for the user watching, so what is shown is what the model was told. The title is not repeated in the result: the model read it in the catalogue when it chose the skill, and what the tag gives it is the id, which is the name it would ask for one by. Each skill loads once per agent, because the instructions stay in the conversation after they arrive and a second copy would say nothing the first did not; a second call is refused and told where to reread it. The bookkeeping is the tool's own state, so two agents reading one skill have each read it once.
- **The call is made with the id and announced with the title**, because the two names exist for two different readers. A model calling a tool needs a name that is short and unambiguous, which is the id; a person watching a run go by needs the sentence somebody wrote to say what the skill is about, which is the title. So `loadskill`'s `Announce` looks the id up and shows the title, and its `Report` shows the directory under it and nothing else — nothing is lost, since that path ends in the id. An id the run does not have is shown as the model wrote it: announcing must not fail, and a call about to be refused is best shown as the call it was. This is the only place a tool shows something other than the argument it was given, and what earns it is that the argument is an identifier with a name for people sitting right beside it.
- Every refusal `loadskill` makes is an error rather than text explaining itself, because no skill was loaded in any of them and that is what a failure is for. An id that is not in the list is refused with the ids that are, since a model one word away from the right id is one correction away from the call it meant. **A call that gave a skill's title is corrected rather than only refused**, and so is a subagent task that names one: it is the one wrong name the list invites, since every skill is listed under both, and a model that reached for the words read the right entry and took the wrong half of it. Naming the id it meant turns the next call into the right one, where a list of every id leaves it to search.
- **A subagent is given the skills its task named, and no others.** A task in a `subagents` call may carry a `skills` array of ids, and that is the only way a subagent gets any: it starts with none, and one that names none reads the prompt a subagent has always read. Naming them costs the spawning agent nothing extra, because it is already deciding what each piece of the work is, and which skills a piece needs is part of that same decision. Skills are the one native tool a subagent can have — it still cannot spawn subagents or end the run, because those tools are not registered for it.
- The ids are checked against the skills the run was given, before anything is spawned, and an id that is not one of them fails the whole call — not just its own task — the way a task with no title does. The model asked for a subagent that knows something, and running it without that answers a question it did not ask; an id it invented is worth correcting, since the next call would invent it again. The refusal names the task, the id that was wrong, and the ids there are. A run given no skills offers no `skills` field on a task and refuses any id, which is the rule that keeps an unregistered tool out of a prompt applied to a field on a call.
- What a task named is resolved once, in the tool, and reaches whatever runs the subagent as `native.Brief.Skills` — the skills themselves, not the ids. The order is the order the run found them and not the order the model wrote them, so the same set of skills reaches a subagent the same way however it was listed, and an id repeated in one task is one skill. A subagent's `loadskill` tool and its skills section are built from that one list, as they are for the run itself, so it has both or neither.
- Nothing records which skills a run was given beyond what is recorded already. The system prompt is in the log and contains the list; every `loadskill` call is a tool call, with its arguments and its result, like any other. A line assembled for either would be a second account of something the log already holds.
- **A hook is a program the user wrote that agi runs around a tool call**, before one is made and after one has produced a result, **or around a message agi is about to print**. `hooks/` is the whole mechanism and it knows nothing of the agent loop, the CLI, or the event log: it is handed a tool's name and the raw JSON arguments the model produced, or the text about to be shown, and it hands back either the data as the hooks left it or an error saying what a hook decided. The feature is described in full in `docs/hooks-specification.md`, which is read when working on hooks and not otherwise; what follows is only what somebody reading this file has to know to avoid contradicting it.
- **The protocol is Claude Code's on purpose, and agi is a flavor of it rather than a copy.** A hook script written for that program should usually work here, so its spellings are kept even where agi would have chosen others — the event names `PreToolUse` and `PostToolUse` in their own capitalization, the JSON object on standard input, the exit statuses, the fields a hook prints back. Where agi cannot mean the same thing it says so rather than pretending — and says it to the user too, not only in a document: it has no interactive permission prompt, so a hook asking to escalate to a person is treated as a refusal **and a note says that is what happened**. Quietly doing something other than what a hook asked is how somebody comes to believe their guard behaves one way when it behaves another, which is the same failure a dead matcher produces. A note is the right shape for it because the hook is not broken and the call really is refused; what the user is owed is the news that a decision meant for a person was made for them. Every divergence is listed in one table in the specification, and a new one is added to that table in the same commit that creates it.
- **agi implements three of Claude Code's events and refuses the rest by name.** A `hooks.json` written against the full list is the likeliest way to name one agi does not have, and a hook filed under an event that never fires is a guard that silently guards nothing, so the name is refused when the folder is read, with the three there are. Adding an event is adding it to `hooks.events` and to the specification; nothing else enumerates them.
- **`MessageDisplay` changes what is printed and nothing else, and that is true by shape rather than by care.** It is handed text agi is about to show and may hand back different text; the conversation, the snapshot and the log keep the model's own words, because the hook runs at the print site and all three have stored the text by the time it gets there. `PostToolUse` keeps the same rule by nobody writing the line that would break it, which is the weaker kind of guarantee. There are four print sites and they are all in `cli/agent.go` — the prose the model writes alongside its tool calls, the final answer, and both halves of a `--schema` run's ending — and they all go through `hooked.say` or `hooked.answer`. Nothing else agi prints is hooked: the rest is agi's own chrome, already styled, and a markdown renderer would mangle it.
- **It follows that a display hook has nothing to refuse and no agent to stop.** The three things that stop an agent exist because a broken guard must never fail open, and a message has already been produced, answered and recorded by the time it is shown — there is nothing to withhold and nothing to fail open into, and ending a run because a renderer is not installed would destroy the work to protect nothing. So a status, a `continue: false`, a refusal and an `additionalContext` are all discarded here, which is what Claude Code does too, and agi differs only in saying so in a note: `hooks.reply.overreached` names the first such request, `Hook.displayed` reads what is left, and `hooks.soften` catches the stops raised where a process is run rather than where its answer is read.
- **The hooks fire when agi displays something and not when it displays nothing, which is definitional rather than a policy about terminals.** A piped run without `--verbose` discards its progress, so there is no display to hook and agi will not spawn a renderer for text nobody will read; the answer is written whatever the destination, so it is always hooked. `output.stepsShown` and `output.answerShown` are what say so, written down in `route`, `quiet` and `nested` rather than worked out by comparing a writer against `io.Discard` — a comparison that is true today by accident of how discarding happens to be spelled. A hook that emits escape sequences into a pipe has corrupted the answer, and that is the hook author's business the way a `bash` guard's rewriting is: agi documents it and does not police it, since one that redacts, translates or trims is worth running into a pipe.
- **A display hook takes no `matcher` and no `if`, and writing either fails the run when the file is read.** Both are defined over a tool and this event has none. Claude Code accepts a matcher here and ignores it, which produces exactly the dead-hook silence that `cli.refuseDeadMatchers` exists to stop, one event along. It follows that `refuseDeadMatchers` asks its question only of a hook whose event is about a tool: one written with a matcher is already gone, and one written without would otherwise pass by luck, since `Hook.Watches` answers true for an absent matcher whatever the event. `Event.AboutTool` is how anything written for a tool call asks whether there is one, and it is a method on the event rather than a list each caller keeps.
- **A matcher is a regular expression and always a regular expression.** Claude Code compares a matcher literally when it happens to be made only of letters, digits, spaces, commas and pipes, and treats it as a pattern otherwise; agi does not, because one rule that always holds is worth more than two told apart by the characters somebody typed. It is matched anywhere in the tool's name, as Claude Code's patterns are, so `^bash$` is how a `hooks.json` asks for exactness. An absent matcher, an empty one, and `*` all mean every tool, and `*` is recognized before anything is compiled since a lone star is not a valid pattern.
- **Claude Code's `Bash(git push *)` form is deliberately not implemented**, because it can only ever target one argument of one tool, and agi's tools — the user's own especially — take several named parameters. A hook's `if` object holds one regular expression per named parameter instead, and the conditions are combined with OR: the hook runs if at least one matches. A parameter the call did not include fails its own condition and is not an error, and a value that is not a string is matched against its compact JSON, so a condition never silently fails to fire. Arguments that are not a JSON object satisfy nothing, and nothing is reported about it: the tool is about to refuse that call and say why.
- **Order is the user's and decides something.** Hooks run in sequence, in the order the folders were named and the order each `hooks.json` lists them, because one hook's output is the next one's input. That is why the event names are read out of the file in a fixed order rather than however a map hands them over: two runs naming the same folders must produce the same list of hooks, which is the invariant that lets a snapshot store no prompt at all, applied one level over.
- **A hook that could never fire is refused when the folders are read.** A matcher accepting no tool the run has — `^Bash$` where the tool is `bash` — otherwise loads, is listed under `--verbose`, and lets the call it was written to guard go straight through, with nothing anywhere saying so; a guard the user believes in and which cannot fire is worse than no guard. `cli.refuseDeadMatchers` asks `hooks.Hook.Watches` against the run's own tool names, which is the widest set any agent holds, so a hook watching `fork` is live even though no subagent could set it off. `Watches` is a method rather than something a caller works out from `Matcher`, because what an absent or wildcard matcher means belongs to the hooks package — a caller comparing strings would have to reimplement the three spellings of "every tool" and would get one wrong eventually. **The same question about a hook's conditions is deliberately not asked**: whether an `if` names a real parameter depends on the tools the matcher accepts, and a tool may declare none or allow any, so the check would hold for some tools and not others, which would read as a guarantee it is not. That is written up as a known limitation rather than half-built.
- **Whether a hook matches is asked when its turn comes, never once for the sequence.** A hook can rewrite a call's arguments, so the call a later hook judges is not the one the model wrote, and deciding the list up front would let one hook turn `ls` into `rm -rf /` and walk it past the guard whose condition is `^rm `. `Set.forEvent` therefore hands over the hooks of an event and nothing more, and `Hook.matches` is asked separately inside the loop. A helper that returned the matching hooks for a call would be that bug waiting to be reintroduced, which is why there is no such helper.
- **A hook's two answers are two error types, and both come back beside the data rather than instead of it.** `hooks.Refusal` is a call that may not be made and reaches the model as a tool failure; `hooks.Stop` is the agent having to end. The report of what ran is returned with either, because the hooks before the one that decided did run and the log is owed their record. It is the same reason `Conversation.AbandonToolRequests` hands back the failures it wrote rather than only writing them.
- **A reply's unknown fields are ignored where a `hooks.json`'s are refused**, and the difference is the point. A `hooks.json` is written for agi, so a field agi does not know is a typo with a silent version. A hook's reply is written for Claude Code's protocol, so a field agi does not know is a field another program reads — `suppressOutput` and `terminalSequence` among them — and refusing it would break a script doing nothing wrong. It is the rule a `SKILL.md`'s frontmatter already follows, applied for the same reason.
- **`--hook-timeout` is a flag and not an environment variable**, for the reason `--resources` and `--max-turns` are: a shell that quietly lowered the time a hook has would make guards fail that would otherwise have passed, and the run it changed would look exactly like one it had not. The timeout is a duration rather than a number, where the two caps are numbers, because it measures time and they count things that have no unit — a bare `30` would leave the user guessing at seconds or milliseconds. Its floor is `hooks.MinTimeout`, checked by the flag's own `Validator`, and it is exported for that check rather than respelled in `cli`, as `native.MinTasks` already is.
- **A hook runs in the folder its `hooks.json` is in, not agi's working directory**, which is the other half of a relative `command` being resolved against that folder rather than a second decision: the exec form's path can be resolved before the program starts, but a shell command line is the user's own text and a path may be anywhere inside it. A hook wanting the project goes there itself, using the `cwd` it is sent. It is a divergence from Claude Code and it is what makes a folder of hooks something that can be moved.
- **The record is never edited by a hook.** A `PreToolUse` hook can change what a tool is handed, and the assistant turn still holds the call exactly as the model wrote it — the request the tool runs on is a copy. What the model *reads* is a different matter: a `PostToolUse` hook's replacement is what goes into the conversation and into the log, because a conversation holding a result nobody was shown would be a record of a run that did not happen. A rewritten answer becomes a plain `ToolResultMessage`, so a structured one is flattened, which is the honest consequence of asking for the output to be replaced.
- **What a hook adds to the conversation waits for the whole batch of calls to be answered.** `additionalContext` arrives as a harness instruction, and an instruction between a request and its result would strand the calls made alongside it — `model.Conversation.Validate` refuses that and a provider would too. So the turn collects them and appends one instruction at the end, several hooks' worth separated by a blank line.
- **A hook can stop an agent three ways and only three**: its program cannot be started, it outran the timeout, or it printed `continue: false`. The first two are divergences from Claude Code, which warns and carries on, and the reason is that a guard which is broken must never fail open. Stopping the run's own agent ends the run — the outstanding calls are answered as abandoned by `cli.halt`, the snapshot is written because `ended` counts it with an interruption and a termination, and the exit status is 1 rather than 130 since the user did not press Ctrl-C. Stopping a fork or a subagent ends only that agent: `cli.contain` catches the sentinel, for the reason it already catches a termination.
- **`hooks.Set` reads a nil receiver as a run with no hooks**, the bargain `eventlog.Log` already makes. The hooks reach every agent through `wiring`, and a caller with nothing to say about them should not have to say `None()` to avoid a crash in the middle of a run.
- The log gains `hook.result` and `hook.failure`, recorded after the fact rather than before. There is no `hook.call`, because a hook is run by a mechanism that hands back an account of what it did and there is no moment in between for a line saying one is about to run; what a hook decided is in `decided`, which is what a reader groups by once the kind has narrowed them. A display hook's line names no tool and no request, because it guarded neither, and both are left out rather than sent empty.
- **A hook that rewrote something records what it left, on its own line.** Rewritten arguments go in `arguments` and everything else a hook can rewrite goes in `content`, so a reader joining a rewrite to the `tool.call` above it reads the two the same way. The line is the only place the text can go: `tool.call` holds the arguments the model wrote and `tool.result` holds what the model finally read, so one line per call would leave every rewrite of a chain but the last unaccounted for, and a display hook's text is in none of the three accounts agi keeps — the conversation, the snapshot and the log all hold the model's own words, so this is the only record of what the user saw. It is kept byte for byte, escape sequences and control codes included, since a hook that paints a message is one whose whole work is those codes and a record with them stripped would not be a record of what was printed; the encoder escapes them and the line stays one JSON object. The text is set together with the decision in `hooks.Report.rewrote`, never beside it, so a line carries a replacement exactly when it says `rewrote`.
- **`terminal/` is the library the terminal tools are built on, and it knows nothing of them.** It runs a program on a real PTY, feeds what it writes to the `charmbracelet/x/vt` emulator, and hands back keys in and screens out — so that an agent can keep a shell, an ssh session or a REPL open across calls, which `bash` cannot, since each `bash` call is one command line on a pipe that is gone when the call ends. It knows nothing of tools, conversations or the agent loop, the way `hooks/` knows nothing of them, so what a tool exposes of a terminal can be decided and redecided without touching how a terminal works. Escape sequences are fed to the emulator and never parsed here: a second parser would be a second opinion about the screen. `tools/workspace/terminal.go` is the one caller.
- **A screen is read back as letters, and styling is deliberately not reported.** What a terminal is for is a session that outlives a call — an ssh connection stayed inside, a REPL, an installer that stops to ask a question, a long job watched while it runs — and in every one of those what the agent needs is the words. So `Text`, `Screen` and the matching behind `Wait` render a cell's content and its width, and a cell's color, bold, underline, reverse video and blink are read by the emulator, kept by it, and never asked for. The emulator still has to read them, since a sequence it did not consume would land on the screen as text; the decision is only that nothing reads what it found. This is not an attempt at a faithful terminal, and faithfulness is a cost rather than a goal. **The limitation that follows is real and is documented rather than fixed**: a program that says something through color alone says nothing here — the selected row of a `whiptail` menu, a search hit highlighted by `less`, a diff whose added and removed lines differ only in color, a prompt that turns red to mean the last command failed. The answer is not a style API added back but driving such a program by what it prints, and in practice the programs that matter do print it: `grep -n`, `diff`, `ls` and `git status --short` all stay readable and correctly aligned with their color thrown away, which `TestStylingLeavesTheTextExactlyAsItIs` holds to by printing one sentence styled and the same sentence plain and requiring the two rows to be the same string. A `Style` type, a `Span` type and a `Cells` method reporting both existed and were removed: nothing read them but their own tests, they named a color the emulator had resolved through its own palette rather than the one the user's terminal would use, and `Cells` had none of the `Lines`/`MaxChars` capping that `Screen` has.
- **Every terminal is closed, and `Close` is the only full guarantee.** It signals every process group in the program's session, not only the program's, because an interactive shell puts each job in a group of its own; a host that dies without calling it still takes the program down through `Pdeathsig` and the PTY hanging up, but the program's jobs only on a best-effort basis, which a test reports rather than fails. Three internals look like simplifications and are not, and each is explained where it is: the PTY master is re-wrapped non-blocking and its `Fd` must never be called again (`openMaster`); the emulator's replies are drained by a goroutine or the first program to ask where the cursor is stops the screen for good (`newScreen`); and the program is forked from a locked OS thread that also reaps it, because `Pdeathsig` fires when a *thread* exits (`ptySession.spawn`). The package is Linux and does not compile elsewhere, which is a TODO in `terminal/terminal.go` and is not to be answered with a no-op. **Known limitation: because `cli` imports the terminal tools whether or not a run enables them, agi as a whole does not build on macOS**, which it did before; there is no runtime error to see, only a compile failure in `terminal/pty.go`. The intended fix is a build tag — the package as it is on Linux, and elsewhere a `Start` that refuses with "terminals need Linux" so only `--enable-terminals` fails — and it is deliberately deferred.
- **Terminals are off unless `--enable-terminals` asks for them, and that is a safety decision rather than a default.** `terminal_open`, `terminal_send`, `terminal_read` and `terminal_close` are workspace tools, peers of `bash`: they act on the machine, they are described by their `Definition` alone, and nothing about them reaches the system prompt. What makes them opt-in is that **a hook cannot guard them**. A `PreToolUse` hook on `terminal_send` sees the keys and not what they run — a command typed over several calls, a line recalled from history or completed with Tab, a shell inside ssh or a REPL, `:!cmd` in vim — so enabling terminals lets an agent past every hook written for `bash`, and the flag's `--help` says so. It is a flag and never an environment variable, for the reason `--resources` is not one. The tool names are reserved against a user-defined tool whether or not the run enables them, so a `tools.json` does not stop loading the day somebody passes the flag; but `refuseDeadMatchers` asks about the tools the run really has, so a hook watching `terminal_send` in a run without terminals is refused as one that could never fire.
- **`--enable-terminals` is one flag with an optional number, and the number caps how many terminals one agent may have open at once.** Bare, it is `workspace.DefaultMaxTerminals`, 8; written `--enable-terminals=N`, it is N. It replaced a switch and a separate `--max-terminals`, because a cap on terminals means nothing in a run without them, and two flags let the user write exactly that and needed a rule refusing it. The optional number is `cli.terminalCap`: urfave/cli never hands the next argument to a flag whose value says it behaves like a boolean, so a bare flag is set to `"true"`, which is the default, and a number has to be attached with `=` — which is also why the help text spells it `[=N]`. The one cost is that `--enable-terminals 5` gives the flag no number and hands the 5 to the prompt, silently ignoring a prompt piped on standard input; `cli.terminalFlags` refuses a prompt that is nothing but a number after a bare flag, naming the spelling that was meant, and urfave gives no access to the raw arguments that would let it ask about position instead. The floor is 1, checked by the flag's `Validator`; there is no ceiling, for the reason `--max-subagents` has none. The cap is per agent and not per run, so a refusal can always be acted on: it lists the agent's own open terminals, every one of which it can close, where a run-wide count would refuse a subagent over terminals only its siblings could close.
- **A terminal belongs to exactly one agent, and ends with it.** `workspace.Terminals` is one agent's set: the run's own agent, each fork and each subagent get a fresh one from `wiring.newTerminals`, and whoever makes one defers its `Close`, which ends what runs in every terminal and everything that started. A fork is a new agent for this purpose though it is a copy in every other: its ids start at 1 whatever its parent had open, it cannot reach its parent's terminals, and its own are closed when it ends — its answer is the only thing that leaves it, so a terminal it left open would be one the parent had never heard of and nothing would close. The run's set is closed by a deferral placed after the log is opened, so it runs before the log is closed. Nothing is opened until an agent asks; a nil `Terminals` is an agent given none and closes as a no-op.
- **Ids are plain numbers from 1, per agent, and never reused.** Never reusing them is what lets "terminal 2 was closed" be told apart from "there is no terminal 7", which are refused in different words because they are corrected differently. Every refusal is a returned error, so the model reads it as a `ToolFailure`. Terminals do not survive from one run to the next and the numbering starts again in each, so the refusal for an unknown id says that a terminal mentioned earlier in the conversation may belong to a run that has ended — the one thing nothing else in a resumed conversation would tell the model. A terminal whose program exited stays in the set: it can still be read, since its last screen is usually the reason, but not typed into, and it holds its place under the cap until closed. **A malformed call is refused in words that say how to correct it**, since the decoder's own message names Go types the model never saw: `workspace.decode` names the parameter and the JSON form it takes when a number arrives as a string or one key as a bare string, and refuses a parameter the tool does not have rather than ignoring it — ignored, `"id": 1` decodes as terminal 0 and is refused as a terminal that does not exist, sending the model after the wrong mistake. An id below 1, which is also what a call that left `terminal` out decodes as, is refused saying the numbers start at 1 and come from the `Opened terminal N.` line. Every description says the same thing up front. **No description mentions the cap**, and the refusal from `Terminals.add` is the only thing that tells the model there is one: almost no run opens enough terminals to reach it, so a sentence warning every run about it is paid for many times over to spare the few, where the refusal arrives exactly when it is useful and cannot have been forgotten by then. It therefore carries everything by itself — how many are open, that this is the limit, which tool undoes it, and which terminals there are to close — and `TestTerminalDescriptionsSayNothingOfTheCap` keeps the warning from creeping back into a description. The count in a `terminal_open` or `terminal_close` result stays: it is feedback on the call just made, not a warning about a limit.
- **The map in `Terminals` is behind a mutex though nothing touches it from two goroutines today.** An agent's tool calls run one after another, and its set is closed after its loop returns. The lock stays because a map read while another goroutine grows it is a fatal error and not a wrong answer, and the facts that make it impossible live in other packages. It is held only to look an id up: a read that waits holds a terminal, not the list of them.
- **The only judgement a call asks of the model is how long to wait, and every wait is exactly what it asked for.** A wait is waited in full whatever the program does meanwhile; only a stopped run cuts it short, reported as the cancellation the way `bash` reports one. There are three: `terminal_read`'s `wait_ms`, and `terminal_send`'s `wait_before_ms` (before typing) and `wait_after_ms` (after typing, before reading). Ending a wait early once output went quiet was tried and taken out: it guesses that a quiet program is a finished one, and the guess is wrong exactly when it matters — a program that prints, sleeps, and prints the line that was being waited for. Waiting for a prompt was tried and taken out too, because nothing on a terminal says when a program is ready: a shell has one prompt, a REPL another, and a program may draw nothing at all. So `terminal_open` waits a fixed second before it reads the first screen, and when keys turn out to have been sent too soon — a program still starting can discard them — the model sees it on the screen, tries again, and waits longer before typing next time, which is what `wait_before_ms` is for. There is deliberately no "wait for this text", since that asks the model to predict the screen. `terminal_send` reads only when given `wait_after_ms` or `lines`, so typing and looking can be one call or two; the combined form is kept on purpose, because typing a command and reading what it did is the commonest thing done with a terminal and two calls for it is a model turn spent every time. **`terminal_send` requires an `explanation`, as `bash` does**, for the same two reasons and one more: asking for the reason makes the model state its intent before acting, it is what the person watching reads first (`terminal 1: <reason>`, then the keys dimmed beneath, in `bash`'s shape), and it stays in the conversation — in a terminal the keys mean whatever the program on the other end makes of them, so why they were typed is harder to work out afterwards than with a shell command. **Every announcement of a call that can wait says how long it waits, zero included**, because the wait is the one judgement the call asked of the model and the reason the screen may sit still while it runs. It goes on a line of its own, dimmed and indented to where the block beneath it starts: `terminal_send` says `(wait 1.5s before typing, 2s after)` under the reason and above the keys, each wait named for its side of the typing, and `terminal_read` says `(wait 2s before reading)` under what it is about to read. Under rather than appended, because what it would be appended to is prose the model wrote and may run to any length, and the waits would then be pushed off the end of a line the user is already reading for its own sake; both tools do it the same way so that the two read alike down the screen. `terminal_open`'s fixed second is not shown, since nothing about it was chosen. Keys are a list of names next to the text rather than escape sequences inside it — a model writing `\x1b` into a JSON string is the mistake the first experiment with this tool made — and every name is checked before anything is typed, so a bad call types nothing.
- **`cmd/agi-term` is a second binary that drives the terminal tools by hand, and exists because a real run is a slow and expensive way to find out what a model sees.** It builds the tools the way an agent builds them — `workspace.NewTerminals`, `Tools()`, `Call` — and prints what they return unchanged, so what a person reads is the string the model would have been handed. That it can be written at all is the proof that the tools are not coupled to the CLI: `tools/workspace` imports only `model`, `tools` and `terminal`, and `tools.Tool` is `Definition` and `Call` and nothing else. **It must never reimplement any part of what it is testing**, since a copy that drifts tests the copy; that rule is what keeps it worth having, and it is why it has no flags, no session, no log and no model. Its language is a line at a time: `-` reads the visible screen, `- 60` reads the last sixty lines, `- 500ms` waits half a second first, `- 500ms 60` does both in either order, anything else is typed with an `ENTER` added after it and read back after a short fixed wait, and end of input closes the terminal. **A typed line reads back because that is what `terminal_send` does**: given a wait or a line count it answers with the screen, given neither it answers `Sent to terminal 1.`, and the combined form is the one a model mostly uses, so a tool for watching what a model sees has to use it too. The wait is a constant and not something the line can set, since the text of the line is the thing being typed and anything else on it would have to be carved back out of a program's own arguments. Reading stays a command of its own for the case the wait was too short and for looking further back than the screen. The numbers are the one thing in it that is not just a line typed at a terminal; the wait earns its place because without it the tool works only at a person's typing speed, since a script piping lines in sends them within a millisecond and reads a screen the program has not drawn yet. **Which number needs the unit was decided by getting it wrong**: a bare number was the wait at first, and the first person to use it read `- 10000` as ten thousand lines and thought the tool had hung. Both readings are reasonable, so the number has to say which it is — and since a bare one is guessed to be lines, it is the wait that carries the `ms`. Keys by name and `terminal_send`'s own waits are not reachable and are a few lines to add if the testing wants them.
- **A terminal does not use `tools.KillGroupOnCancel`, and does not need to.** Its program is a session leader on its own PTY, and `Terminal.Close` signals every process group in that session, which is the same guarantee for a program whose jobs each get a group of their own. Cancelling a call does not close a terminal — a terminal outlives its calls by design — so the guarantee arrives when the agent ends rather than when a call is cancelled.
- Running a gateway is the user's concern, not the repository's. Do not add Docker Compose files, container definitions, or other deployment manifests here.

## Environment variables

Every environment variable the application reads. Keep this table complete —
adding one to the code without adding it here is an incomplete change.

| Variable          | Read by            | Required | Meaning                                                                                              |
| ----------------- | ------------------ | -------- | ---------------------------------------------------------------------------------------------------- |
| `AGI_VERBOSE`     | `cli`              | No       | Enables verbose output, equivalent to the `--verbose` / `-v` flag. Any non-empty truthy value enables it. |
| `AGI_BACKEND`     | `cli`              | Yes      | Which backend a run talks to: `litellm` or `openai`. There is no default; a run that names none is refused with the list of names. |
| `LITELLM_URL`     | `transport/litellm` | For `litellm` | Base URL of a LiteLLM gateway, for example `http://localhost:4000`. Setting it is what enables the gateway; there is no default. Must be an `http` or `https` URL. |

| `LITELLM_MODEL`   | `transport/litellm` | No      | Model to ask the gateway for. Defaults to `deepseek-chat`.                                            |
| `OPENAI_URL`      | `transport/openai` | For `openai` | Base URL of an OpenAI-compatible endpoint, for example `https://api.deepseek.com`. Setting it is what enables the backend; there is no default. Must be an `http` or `https` URL. |
| `OPENAI_KEY`      | `transport/openai` | No       | Bearer token presented to the endpoint. Omit it for an endpoint that needs no authentication, such as a model served on the local machine. |
| `OPENAI_MODEL`    | `transport/openai` | No       | Model the agent runs on. Defaults to `deepseek-chat`, which suits the default base prompt.                                                 |

Read by the standard library rather than by agi. Defaults to `/tmp`. `--session` overrides it for the session's own directory, never for `mktemp`. |

## Layout

| Path                 | Contents                                                          |
| -------------------- | ----------------------------------------------------------------- |
| `main.go`            | Entry point; wires the CLI and maps errors to an exit status.      |
| `cmd/agi-term/`      | A second binary, for testing only: drives the terminal tools by hand from standard input and prints what they return. Not on the path a run takes. Linux only, as `terminal/` is. |
| `cli/`               | Command tree, flags, command actions, backend selection, and the agent loop. |
| `model/`             | Core domain types (messages, conversations, schemas) and their validation. |
| `transport/`         | The `Client` and `Backend` interfaces backends implement, plus request/response. |
| `transport/openai/`  | The OpenAI chat completions protocol and the HTTP client that speaks it, which every backend is a configuration of. |
| `transport/litellm/` | A LiteLLM gateway's configuration of that client, read from the environment. |
| `tools/`             | The `Tool` contract, the registry that collects them, and what every tool that runs a program shares: cutting an oversized result down, and making sure a cancelled one leaves nothing behind. |
| `prompt/`            | The system prompts, one Markdown file each, compiled in with `go:embed`. |
| `tools/native/`     | Tools that are part of the agent itself, explained in the system prompt, one guidance file each. Currently `subagents`, `fork`, `terminate`, and `loadskill`. |
| `tools/workspace/`   | Optional tools that do work on the machine. Currently `bash`, `mktemp`, `patchfile`, `writefile`, and, with `--enable-terminals`, `terminal_open`, `terminal_send`, `terminal_read` and `terminal_close`. |
| `tools/userdefined/` | Tools the user wrote themselves: a folder's `tools.json`, the schema a call is checked against, and running the executable it names. |
| `skills/`            | Finding the skills under a folder: the traversal, the `SKILL.md` frontmatter it reads, and the rules a skill has to keep. |
| `hooks/`             | Programs the user wrote that run before and after a tool call, and as agi is about to print something the model wrote: reading a folder's `hooks.json`, deciding which of them a call matches, and running them. The whole feature is `docs/hooks-specification.md`. |
| `terminal/`          | A program on a real PTY, rendered by an emulator, driven by keys and read back as a screen of text, styling left out. The library the terminal tools are built on. Linux only. |
| `session/`           | Storing a run in a directory and resuming it, with its own file format; owns where the log and the file backups go, and the lock that keeps one run to a session. |
| `eventlog/`          | The run's event log: one JSON object per line, written to the session's directory. |
| `docs/`              | Long-form documents about one feature each: what it does, and why it was built that way. Read one only when working on what it is about — see the rule below. |
